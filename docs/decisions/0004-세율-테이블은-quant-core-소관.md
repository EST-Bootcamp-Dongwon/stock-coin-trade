# ADR-SC-0004 — 날짜 기반 증권거래세 테이블은 여기 넣지 않는다 (`quant-core` 소관)

- **상태**: 채택
- **날짜**: 2026-08-17
- **관련**: [ADR-SC-0002](0002-체결엔진-원본과-이식.md) · `ADR-QC-0003`(삭제됨 — `quant-core` 저장소 제거) · `quant-contract/CONTEXT.md` §4(삭제됨 — `quant-contract` 저장소 제거)

> ⚠️ **2026-09-15 갱신** — `quant-core`·`backtest-service` 는 개발하지 않기로 해 제거됐다.
> 이 ADR 의 전제("여기 넣지 않는다, `quant-core` 가 만든다")가 사라졌다 — 세율표를
> 만들 `quant-core` 자체가 없다. **날짜 기반 세율표가 실제로 필요해지면 이 저장소에서
> 다시 결정해야 한다.** `cost_rates(account)` 를 그대로 쓴다는 결론은 바뀌지 않는다.

## 맥락

상위 리서치(03번 검증완료본 §3 P0-3, `CONTEXT.md` §4)가 P0 로 지적한 사항이 있다.

> 10년 백테스트(2016~2026) 구간에서 매도 세율이 **일곱 번** 바뀐다.
> 단일 세율을 전 구간에 적용하면 구간마다 과대·과소평가가 뒤집힌다.

| 적용 기간 | 코스피 (거래세 + 농특세 0.15%) | 코스닥·K-OTC | 실부담 |
|---|---|---|---|
| ~2019-05 | 0.15% + 0.15% | 0.30% | 0.30% 🔍 |
| 2019-06 ~ 2020-12 | 0.10% + 0.15% | 0.25% | 0.25% 🔍 |
| 2021-01 ~ 2022-12 | 0.08% + 0.15% | 0.23% | 0.23% |
| 2023 | 0.05% + 0.15% | 0.20% | 0.20% |
| 2024 | 0.03% + 0.15% | 0.18% | 0.18% |
| 2025 | 0.00% + 0.15% | 0.15% | 0.15% |
| 2026 ~ | 0.05% + 0.15% | 0.20% | **0.20%** |

그래서 `cost_rates(trade_date, market)` 로 바꾸라는 지시가 이 저장소 세션 프롬프트에도 들어왔다.

**그런데 이 저장소의 `cost_rates()` 는 그런 함수가 아니다.**

```python
def cost_rates(account: Account) -> tuple[Decimal, Decimal]:
    if account.is_contest and account.contest_id:
        return Decimal(account.contest.fee_bp), Decimal(account.contest.tax_bp)
    fee_key, tax_key = PRACTICE_RATE_KEYS.get(account.asset_class, ...)
    return _setting_bp(fee_key), _setting_bp(tax_key)
```

요율은 **날짜가 아니라 계좌**에서 나온다. 그리고 그 이유가 코드 주석에 이미 적혀 있다.

> `AppSetting` 에 두면 값을 고치는 순간 **진행 중인 대회의 규칙이 바뀐다.**
> 타임폴리오도 SK하이닉스 편입 예외를 대회 중간에 도입한 전례가 있어(F-04 3.1),
> **"규칙은 대회마다 다르고 기간 중에도 다를 수 있다"** 가 전제다.

## 결정

**날짜 기반 증권거래세 테이블을 이 저장소에 넣지 않는다.**
`cost_rates(account)` 를 그대로 유지한다. 세율표는 `quant-core.matching.cost` 에서 만든다.

## 근거

**두 시스템의 시간 축이 다르다.**

| | `stock-coin-trade` | `quant-core` / `backtest-service` |
|---|---|---|
| 언제를 사는가 | **지금** — 실시간 모의투자 대회 | **과거 10년** — 백테스트 |
| 요율의 출처 | 대회 주최자가 정한 규칙 (`Contest.fee_bp`) | 그날의 법령 |
| 요율이 바뀌는 이유 | 대회가 다르니까 | 시행령이 개정됐으니까 |
| 2026년 매도세 | 대회가 0bp 라고 하면 **0bp 다** | 20bp 다 |

여기에 날짜 테이블을 넣으면 **대회 규칙 엔진이 법령에 덮인다.** "수수료 0원 이벤트 대회"
같은 것을 만들 수 없게 되고, 진행 중 규칙 변경이라는 명시적 설계 전제가 무너진다.
반대로 `quant-core` 에 계좌 개념을 넣으면 그쪽이 Django 를 알아야 한다 — 이식이 불가능해진다.

**둘 다 맞는 모델이고, 서로의 자리가 다르다.** 상위 리서치가 지적한 P0 는 유효하다 —
다만 그것이 겨냥한 대상이 백테스트 엔진이지 대회 플랫폼이 아니다.

## 결과

- ✅ 대회 규칙 엔진이 온전하다. `Contest.fee_bp`/`tax_bp` 가 계속 정본이다.
- ✅ `quant-core` 이식 시 `calc_cost(gross, side, fee_bp, tax_bp)` 는 **그대로 간다** —
  이미 요율을 인자로 받는 순수 함수라 시간 축과 무관하다.
  `trading/golden_test.py` 의 `test_calc_cost_골든` 이 그 값을 고정해 뒀다.
- ✅ 갈라지는 지점은 `cost_rates` **하나뿐**이다. `quant-core` 는 `sell_tax_bp(date, market)` 를
  자기 쪽에 두고, 이 저장소는 `cost_rates(account)` 를 유지한다. 둘 다 `calc_cost` 를 먹인다.
- ⚠️ 🔍 표시한 2020년 이전 두 줄은 **증권거래세법 시행령 연혁에서 직접 확인해야 한다.**
  그 확인은 세율표를 실제로 만드는 `quant-core` 세션의 몫이다.
- ⚠️ 이 저장소에 "10년 백테스트" 기능을 넣게 되면 이 결정을 다시 봐야 한다.
  그때는 백테스트 경로가 `quant-core` 를 부르면 되므로, 여전히 테이블을 여기 복사하지는 않는다.
