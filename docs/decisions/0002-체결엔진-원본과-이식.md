## 맥락

`trading/services.py` 의 체결 엔진(1,132줄)은 이 프로젝트군에서 **가장 값어치 있는 자산**이다.

- `resolve_limit_price()` — 가격 유형 4종 → 단일 지정가 (상·하한가 특례 포함)
- `match_orderbook()` — 10호가 실제 소진 + 11호가 이후 가정 체결
- `calc_cost()` — bp 정수 + `Decimal`, 원 단위 절사
- `apply_fills()` — 현금·평단·실현손익 반영의 **유일한 진입점**

`FillResult`/`Fill` 이 이미 ORM 이 아닌 `dataclass` 라, Django 의존성 없이 재사용할 수
있는 상태에 가깝다. `backtest-service` 는 이 로직이 필요하지만 Django 를 끌어올 수 없다.

두 가지 실패 방식이 있다.

1. **양쪽에 복사한다** → 한쪽만 고쳐지고 조용히 갈라진다. 백테스트와 모의투자의
   체결 결과가 달라지는데 아무도 모른다.
2. **여기서 들어내 `quant-core` 로 옮긴다** → 이 저장소가 껍데기가 되고,
   개인 프로젝트로서의 완성도(강사님 요건)를 잃는다.

## 결정

**이 저장소가 체결 엔진의 원본이다. `quant-core` 는 순수 함수만 이식해 가고,
이 저장소는 그 이식본을 다시 import 해서 계속 돈다.**

- 이식 방향은 한 방향이다: `stock-coin-trade` → `quant-core`. 반대는 없다.
- 이식은 **재작성이 아니라 경계 이동**이다. `_apply_buy`/`_apply_sell` 안의
  `account.save()`·`position.save()` 를 호출부로 밀어내는 것이 작업의 본체다.
- 이식 후 이 저장소에는 얇은 **adapter 층**만 남는다.
- 🔒 **이 저장소는 이식이 끝난 뒤에도 계속 돌아야 한다.** 그것이 이식이 맞았다는 증거다.

## 근거

**"돌아가는 것" 이 회귀 테스트다.** `quant-core` 에 순수 함수만 있으면 그 함수가
현실의 주문 흐름에서 맞게 동작하는지 아무도 모른다. 이 저장소가 실제 계좌·포지션·
대회 규칙을 붙여 돌리고 있으므로, **이식본이 여기서도 같은 답을 내면 이식이 맞은 것**이다.

그래서 순서가 정해진다.

```
① 골든 테스트로 현재 값 고정   ← 이게 없으면 ②③을 구분할 수 없다
② 경계 이동 (account.save() 제거)
③ quant-core 로 이식 + 같은 골든 값으로 대조
④ 이 저장소는 adapter 로 다시 붙인다
```

**①을 건너뛰면 "세율 때문에 바뀐 것" 과 "리팩터링 때문에 깨진 것" 을 구분할 수 없다.**

## 결과

- ✅ `trading/golden_test.py` 23건이 순수 함수의 값을 고정했다 (DB 미사용).
  `quant-core` 쪽에서 같은 입력을 넣어 `__snapshots__/golden_test.ambr` 와 대조하면 된다.
- ✅ 체결 규칙이 한 곳에만 존재한다 — 백테스트와 모의투자가 갈라지지 않는다.
- ⚠️ `apply_fills` 는 아직 순수하지 않아 골든 테스트에 없다.
  무엇을 어디로 미는지는 [경계표](../how-to/quant-core-이식-경계표.md) 에 있다.
- ⚠️ `quant-core` 가 생기면 이 저장소에 **의존성이 하나 늘어난다**(`pip install quant-core`).
  그전까지는 `trading/services.py` 가 그대로 정본이다.
