## 6. 문서 규칙

### 6.1 버전 정책

| 변경 | 버전 |
|---|---|
| 스택·도메인 구조 변경 (예: 모드 체계 변경) | **Major** +1.0 |
| 기능 추가·규칙 수치 변경 | **Minor** +0.1 |
| 오탈자·표현 | 버전 유지 |

**작업 중에는 버전업하지 않는다.** 변경 노트를 누적했다가
한 기능·마일스톤 완료 후 **통합본 + 요약본 + 변경사항 3종을 동시 생성**한다.

### 6.2 문서 분리 원칙

사용자 방침: **통합본과 개별 문서를 둘 다 유지한다.**

| 축 | 이유 |
|---|---|
| 통합본 (`00-통합-기능명세서`) | 전체를 한 번에 훑을 때 |
| 개별 문서 (`F-xx` · `U-xx` · `A-xx`) | **버전 업데이트 시 해당 문서만 고치면 되어 편집·리뷰가 쉽다** |

### 6.3 미러링

- 로컬 작업 폴더: `projects/stock-coin-trade/docs/`

### 8.1 세션 7 실측 결과 (2026-08-13)

**전제 3 — pykrx 는 관리종목·투자경고를 주지 않는다. 상장일도 없다.**
`pykrx.stock` 공개 함수 90개를 전수 확인했다. 폴백으로 적어 둔 "KRX 공개 API 직접
파싱"은 **채택하지 않았다** — [F-16](v2-design/features/version2.0/F-16-시장데이터-파이프라인.md) 4장이
"깨지기 쉬워서 버린다"고 명시한 경로를 되살리게 된다. 세 필드는 **배치가 건드리지 않고**
Admin 에서 운영자가 관리한다 (→ 변경노트 E-17).

**전제 3-보 — KRX 데이터포털이 로그인을 요구하도록 바뀌었다.** 문서 전체가
"pykrx 는 그냥 된다"를 전제로 쓰였으나 이제 `KRX_ID`·`KRX_PW` 가 **착수 준비물**이다
(→ 변경노트 E-16).

**전제 5 — 모델 로드 15.7초 · 21건 임베딩 0.24초.**

| 구간 | 실측 |
|---|---|
| fastembed 모델 로드 (캐시 있음) | **15.7초** |
| 임베딩 1건 | 0.25초 |
| 임베딩 21건 | 0.24초 |
| 최초 실행 전체 (220MB 다운로드 포함) | 43초 |

**비용은 전부 모델 로드다. 연산은 사실상 공짜다.** 두 가지가 따라 나온다:

1. **문서 임베딩을 배치로 뺀 판단이 옳았다** ([E-06](v2-design/erd/version2.0/E-06-insight.md) 2.5).
   규약 8.2 의 실행처 판정도 **로컬 CPU** 가 맞다 — GPU 는 0.24초를 줄일 뿐이다.
2. **[E-06](v2-design/erd/version2.0/E-06-insight.md) 2.5 의 "검색 쿼리 임베딩은 동기" 는
   다시 봐야 한다.** "짧은 문장이라 부담이 작다"는 연산만 본 것이고, 서버리스
   콜드스타트에서는 **매 검색이 15.7초**가 된다. 폴백(Edge Function 이전) 또는
   상시 기동 프로세스에 모델을 상주시키는 선택이 필요하다.
   → **F-15 지식검색 RAG 구현 세션의 착수 결정 항목**으로 넘긴다.

### 8.2 세션 11 실측 결과 (2026-08-17)

**전제 6 — 임베딩은 Supabase 를 잠식하고 있지 않다. 한 건도 없다.**

상위 설계 문서(`quant-contract/CONTEXT.md` §2)는 "insight 의 fastembed 임베딩이
Supabase 500MB 를 이미 쓰고 있다"고 적었고, §9 는 이것을 **"저장소 결론을 바꿀 수 있는
유일한 변수"** 로 최우선 미해결에 올려 두었다. 직접 재 보니 사실이 아니었다.

| 항목 | 실측 (프로젝트 `sgbhrahtewojmicwmxxu`) |
|---|---|
| DB 전체 | **16 MB / 500 MB → 3.2%** |
| `knowledge_document` 행 수 | 21 |
| 그중 **임베딩이 든 행** | **0** |
| 가장 큰 테이블 | `snapshot_holding` 984 kB (2,862행) — 임베딩이 아니라 **대회 스냅샷**이다 |

`fastembed` 가 배포 번들(slim)에서 빠져 있어 Vercel 에서는 임베딩 생성 경로가 아예
돌지 않았고, 로컬에서도 아직 채우지 않았다. **없는 문제였다.**

따라서 "임베딩을 로컬 DB 로 옮긴다" 는 계획을 **보류**한다. 재검토 조건을 수치로
못박아 두었다 (DB 250MB 초과 · 임베딩 10,000행 초과 · 스냅샷 월 100MB 초과 중 하나).
→ [ADR-SC-0003](decisions/0003-insight-임베딩-저장위치.md)
