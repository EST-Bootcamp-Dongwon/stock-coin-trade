## 0. 읽는 법

### 0.1 v1.0 아키텍처 한눈에

```
브라우저 (Vanilla JS · Tailwind CDN · 서버 렌더링 없음)
   │
   ├── nginx (:80 → 컨테이너 3000)
   │     ├── /            → 정적 파일 (.html 확장자 생략 + SPA fallback)
   │     ├── /api/*       → python-backend:8200   (세션 쿠키 전달)
   │     ├── /openapi/*   → python-backend:8200   (Bearer API Key, 쿠키 없음)
   │     ├── /upbit-api/* → https://api.upbit.com/v1/*   (CORS 우회 중계)
   │     └── /upbit-websocket → wss://api.upbit.com/websocket/v1
   │
   └── Flask 3 (단일 프로세스, blueprint 10개) ── SQLAlchemy 2 ── MariaDB 11.4
         └── APScheduler (프로세스 내 백그라운드 스레드)
         └── Qdrant (기본 `:memory:` — 재기동 시 사용자 추가 문서 소실)
```

**Flask blueprint 10개** = `member` · `crypto_market` · `trade` · `admin` · `ai` · `ai_sheet` ·
`stocks` · `api_keys` · `openapi` · `alternatives`.
그 외 라우트 12개는 `app.py` 에 직접 등록되어 있다(종목 목록·검색·지수·시세·차트·movers·
배치시세·시총랭킹·Qdrant 4종·KRX뉴스).

### 0.2 분류 두 축

사용자 확정(2026-08-11): **기능 관점**과 **구현 관점**을 각각 별도 열로 표시한다.

| 열 | 의미 | 값 |
|---|---|---|
| **기능** | 사용자가 보는 기능이 v2.0 에서 어떻게 되는가 | `살림` / `개선` / `대체` / `신규흡수` |
| **구현** | 코드를 얼마나 재사용할 수 있는가 | `포팅` / `수정포팅` / `재작성` |

- **기능·살림** = 화면과 동작을 v1.0 그대로 유지.
- **기능·개선** = 같은 기능이되 범위·UX·정확도를 확장.
- **기능·대체** = 기능 목적은 유지하되 수단을 갈아끼움 (예: APScheduler → Supabase pg_cron).
- **기능·신규흡수** = v1.0 기능이 v2.0 의 대회(Contest) 도메인 안으로 편입됨.
- **구현·포팅** = 로직을 거의 그대로 옮김 (언어·프레임워크 문법만 변환).
- **구현·수정포팅** = 로직 뼈대는 재사용하되 손봐야 함.
- **구현·재작성** = 버리고 새로 씀.

> ⚠️ Flask → Django 전환은 **전 기능 공통 전제**이므로 구현 열에 매번 적지 않는다.
> 구현 열은 "Django 로 옮길 때 로직을 얼마나 재사용하는가"만을 뜻한다.

### 0.3 v2.0 확정 전제 (직전 세션)

- 스택: **Django + DRF + HTMX/Alpine/Tailwind + Supabase Postgres**
- 스케줄러: **Supabase pg_cron** (Vercel Hobby cron 은 하루 1회·UTC·±1시간이라 불가,
  APScheduler 는 서버리스에서 죽음)
- **대회(Contest) 도메인 전면 도입.** 기간 1달, 이후 팀프로젝트로 이관·발전
- 디렉토리: Django 는 `backend/` 신규, 기존 `python-stock-backend/`·`frontend/` 는 `legacy/` 로 보존

### 1-1. 회원 (Member)

| 항목 | 내용 |
|---|---|
| **화면** | `/member/register.html` · `/member/login.html` · 전 화면 공통 GNB 우측 사용자 영역 |
| **API** | `POST /api/member/register` · `POST /api/member/login` · `POST /api/member/logout` · `GET /api/member/me` |
| **DB** | `member` (member_id, username, email, password, asset) — `CHECK (asset >= 0)` |
| **외부 의존성** | 없음 |
| **구현 파일** | `python-stock-backend/members.py` · `frontend/js/common.js`(헤더·세션) |

**동작 상세**
- 가입 시 **초기 자산 1억 원**(`INITIAL_ASSET = 100_000_000`)을 즉시 지급하고 곧바로 로그인 처리.
- 비밀번호는 **bcrypt** 해싱. 세션은 **Flask 서명 쿠키**, 유효기간 7일(`PERMANENT_SESSION_LIFETIME`).
- 검증은 필드 단위로 `{"field": "email", "error": "..."}` 형태를 반환해 프론트가 해당 입력칸에 표시.
- **`member.asset` 하나가 현금 잔고의 단일 원천**이다. 주식·코인·대체자산이 이 한 칸을 공유한다.

**v2.0 분류**

| 기능 | 구현 | 근거 |
|---|---|---|
| **개선** | **재작성** | Django `AbstractUser` 기반으로 갈아엎는다. `member.asset` 을 계정에 직접 두는 구조는 **대회 도메인과 충돌**한다 — 대회마다 참가 계좌가 따로 있어야 하므로 `Account`(회원×대회) 를 분리해야 한다. 비밀번호 해싱·세션은 Django 기본 제공으로 대체. |

**v2.0 개선 항목**
- `Member` ↔ `Account`(회원×대회) 분리. 잔고·포지션·주문은 전부 `Account` 에 매단다.
- 이메일 인증 / 소셜 로그인 여부 결정 필요 (v1.0 에 없음).
- 프로필(닉네임·아바타) — 대회 랭킹 화면에 노출할 최소 정보 필요.

### 1-2. 코인 거래 (Crypto Trade)

| 항목 | 내용 |
|---|---|
| **화면** | `/trade/order.html` |
| **API** | `GET /api/crypto/market-list` · `GET /api/crypto/<code>` · `GET /api/crypto/<code>/domestic-prices` · `GET /api/crypto/rankings` · `GET /api/trade/hold` · `POST /api/trade/order/buy` · `POST /api/trade/order/sell` |
| **DB** | `upbit_market` · `hold_crypto` · `crypto_rank` · `member`(현금 차감) |
| **외부 의존성** | **Upbit** REST(`/v1/ticker`) + WebSocket(ticker) · **Bithumb** · **Coinone** · **Korbit** · **CoinMarketCap**(랭킹 동기화) |
| **구현 파일** | `python-stock-backend/crypto.py` · `frontend/js/order.js` |

**동작 상세**
- **실시간 시세**: nginx 가 `/upbit-websocket` 으로 중계. 브라우저가 업비트에 직접 붙지 않으므로
  운영 도메인에서 CORS 에 막히지 않는다(`proxy_set_header Origin "";` 가 핵심).
- **국내 4대 거래소 시세 비교**: 업비트·빗썸·코인원·코빗을 동시 조회해 한 줄로 나열. 개별 실패는
  `null` 로 흘려보내 화면이 죽지 않는다(`_fetch_price_safely`).
- **매수**: 원화 금액(`buyKrw`) 입력 → 현재가로 나눠 수량 산출(소수점 8자리). 기존 보유가 있으면
  평단 재계산. `member.asset` 차감. **`SELECT ... FOR UPDATE` 로 행 잠금** 후 검증→차감.
- **매도**: 수량(`sellCount`) 입력 → 보유 수량 검증 → 매수원금을 비율만큼 차감하고 평가금액을 현금에 가산.
  수량이 0 이 되면 보유 행 삭제.
- 관심코인(⭐)은 `localStorage`(`CRYPTO_WATCH_KEY`) 에만 저장 — **서버에 없다.**
- 코인 차트는 Lightweight Charts.

**v2.0 분류**

| 기능 | 구현 | 근거 |
|---|---|---|
| **신규흡수** | **수정포팅** | 매수/매도 체결 로직(평단 재계산·행 잠금)은 검증된 로직이라 뼈대를 살린다. 다만 잔고 주체가 `member` → `Account` 로 바뀌고, 주문이 **대회 기간 내에서만** 유효해야 하므로 진입 검증이 추가된다. |

**v2.0 개선 항목**
- **코인 주문 이력 테이블이 없다.** 주식은 `stock_order` 가 있는데 코인은 `hold_crypto`(현재 보유)만
  있어 **체결 이력을 복원할 수 없다.** → `CryptoOrder` 신설 필수. (→ 1-5 거래이력, 4장 결함 D-4)
- 관심코인을 서버 저장으로 이동 (기기 간 동기화).
- `crypto_rank`(CoinMarketCap Top 100) 는 USD 기준이고 거래는 KRW 기준이라 **두 데이터가 연결되어
  있지 않다.** 대회 랭킹에는 쓰이지 않으므로 v2.0 에서 존치 여부 결정 필요.

### 1-3. 주식 거래 (Stock Trade)

| 항목 | 내용 |
|---|---|
| **화면** | `/trade/stock.html` (전체 화면 중 **최대 규모** — HTML 492줄 · JS 858줄) |
| **API** | `GET /api/stocks/list` · `/search` · `/quote` · `/chart` · `/market` · `/movers` · `/prices` · `/market-cap-rankings` · `GET /api/stocks/account` · `/positions` · `/orders/history` · `POST /api/stocks/orders/buy` · `/sell` · `POST /api/stocks/account/reset` |
| **DB** | `stock_position` (UNIQUE member_id+symbol) · `stock_order` · `member`(현금) |
| **외부 의존성** | **yfinance**(1순위) → **네이버 금융**(2순위, `m.stock.naver.com` · `api.finance.naver.com` · `polling.finance.naver.com`) → **시뮬레이션**(3순위) · **KRX KIND** 상장법인 목록 |
| **구현 파일** | `stock_market.py`(492줄) · `stock_trading.py` · `stocks.py` · `frontend/js/stock.js` |

**동작 상세 — 3단 폴백 시세**
1. `yfinance` 로 `005930.KS` 형태 조회
2. 실패 시 네이버 금융 국내 API (6자리 숫자 종목코드만)
3. 그래도 실패하면 **수업용 14종(`STOCKS`)에 한해서만** 기준가 기반 시뮬레이션 가격 생성.
   KRX 에서 검색해 들어온 종목은 **가짜 가격으로 주문되지 않도록 503 을 던진다.**

**종목 유니버스 2겹**
- `STOCKS` 14종(KOSPI 9 + KOSDAQ 5): 이름·시장·섹터·티커가 **하드코딩**. 대시보드·시총랭킹·
  시뮬레이션 폴백은 이 14종만 대상.
- `get_krx_stocks()`: KRX KIND 상장법인 목록 전체를 **하루 1회 캐시**(EUC-KR HTML 정규식 파싱).
  검색·주문은 이 전체 목록을 대상으로 한다.

**캐시 TTL** — 시세 60초 · 차트 300초 · 지수 60초 · 대시보드 다종목 30초 · KRX 목록 86400초.
전부 **프로세스 메모리 dict**. 워커가 늘면 캐시가 갈라진다.

**주문 처리** (`stock_trading.execute_order`)
- `db.refresh(member, with_for_update=True)` 로 회원 행 잠금 → 잔고 검증 → 차감 → 포지션 갱신 →
  `stock_order` 기록. 매수 시 평단 = `int(총매수금액 / 총수량)`.
- **수수료·세금 없음. 지정가 없음. 전량 시장가 즉시 체결.**
- `source` 컬럼으로 주문 경로 구분: `WEB` / `PINE` / `OPENAPI` / `DEMO_SEED`.

**화면 기능** (벤치마킹 반영분)
- ⭐ 관심종목(localStorage) · 📋 호가창 5단계(현재가에서 **파생 생성** — 실제 호가 아님) ·
  📈 상승/하락 TOP 3 · 🥧 포트폴리오 도넛(Highcharts) · 🔄 계좌 초기화 · 🔍 종목 검색 ·
  🗂️ 시장 탭(전체/KOSPI/KOSDAQ/⭐) · 💡 손익분기가 · 이동평균선 토글 · %비율 주문 버튼

**계좌 초기화**(`POST /api/stocks/account/reset`)
- `stock_position` · `stock_order` · `alternative_position` · `alternative_order` 를 삭제하고
  현금을 1억으로 되돌린다. **코인 보유(`hold_crypto`)는 지우지 않는다.** (→ 4장 결함 D-5)

**v2.0 분류**

| 기능 | 구현 | 근거 |
|---|---|---|
| **신규흡수** | **수정포팅** | 체결 엔진(`execute_order`)과 3단 폴백 시세(`stock_market.py`)는 v1.0 의 핵심 자산이라 살린다. 다만 화면은 대회 계좌 기준으로 재구성되고, 시세 폴백은 캐시를 프로세스 메모리 → Redis/DB 로 옮겨야 한다(서버리스에서 메모리 캐시는 무의미). |

**v2.0 개선 항목**
- 캐시를 **프로세스 메모리 → 공유 캐시**로 (서버리스·다중 워커 대응).
- 호가창을 "파생 생성"이라고 화면에 명시하거나, 실제 호가 API 로 교체.
- 수수료·거래세 모델 도입 여부 결정 (대회 순위 공정성과 직결).
- 지정가·예약 주문 (대회 요소로서 매력적).
- `STOCKS` 14종 하드코딩을 DB 테이블로 이관.

#### v1.0 (강사님 구현) — 채택된 기준선

순수 계산기다. 보유 수량·보유 평균가·추가 매수가를 **직접 타이핑**하면 결과가 나온다.

- **정방향**: 추가 매수 금액 · 추가 매수 수량 · 총 보유 수량 · 총 매수 금액 ·
  **신규 평균 매수가** · 평균가 변동률
- **수량/금액 입력 모드 전환** (라디오 버튼)
- **목표 평균가 역산**: 목표 평균가 입력 → 필요한 추가 매수 수량·금액·도달 시 총 수량.
  역산 공식 `requiredQty = holdQty × (holdAvg − targetAvg) / (targetAvg − buyPrice)`
- 도달 불가능한 목표(목표가가 보유 평단과 추가 매수가 사이가 아닌 경우)를 감지해 안내.

#### 우리 구현 (`899ac83`) — v2.0 요구사항으로 이관 ★

우리가 만든 것은 **독립 페이지가 아니라 주식 거래 화면 안의 시뮬레이션 모달**이다
(`frontend/js/stock.js` +342줄 · `frontend/trade/stock.html` +136줄).
강사님 구현을 v1.0 기준으로 채택하되, **아래 고급 기능을 v2.0 개선 항목으로 명시한다.**

### 1-7. OpenAPI (외부 연동)

| 항목 | 내용 |
|---|---|
| **화면** | `/openapi.html`(명세 문서) · `/member/api-keys.html`(키 관리) |

| **키 관리 API** | `GET /api/member/api-keys` · `POST /api/member/api-keys` · `DELETE /api/member/api-keys/<id>` |

| **구현 파일** | `openapi.py` · `api_keys.py` · `frontend/js/api-keys.js` |

**동작 상세**
- 키 형식 `eduapi_live_<token_urlsafe(32)>`. **평문은 발급 시 1회만 반환**하고 DB 에는
  `sha256(raw)` 만 저장. 목록에는 `key_prefix`(앞 16자) 만 보여준다.
- 인증: `Authorization: Bearer <key>`. 폐기는 soft delete(`is_active = False`).
- **Rate limit**: 키당 **분당 60회**. 구현은 `dict[api_key_id] → [timestamp...]` 슬라이딩 윈도우 +
  `threading.Lock`. **프로세스 메모리** — 재기동·다중 워커에서 초기화된다.
- `last_used_at` 을 매 호출마다 갱신.
- 주문은 `source="OPENAPI"` 로 기록되어 거래이력에서 구분된다.

**v2.0 분류**

| 기능 | 구현 | 근거 |
|---|---|---|
| **살림** | **수정포팅** | 대회 참가자가 **자기 봇으로 매매**할 수 있게 하는 기능이라 대회 도메인과 궁합이 매우 좋다. 키 발급·해싱·soft delete 로직은 그대로 포팅. Rate limit 만 **메모리 → Postgres/Redis** 로 대체해야 서버리스에서 동작한다(→ 기능은 살리되 수단은 대체). |

**v2.0 개선 항목**
- Rate limit 저장소를 공유 저장소로 이동 (**필수** — 이걸 안 하면 서버리스에서 무력화됨).

**동작 상세**
- **Pine Script 를 브라우저에서 정규식으로 파싱**한다. 진짜 인터프리터가 아니다.
  - 지원 지표: `ta.sma` · `ta.ema` · `ta.rsi` (전부 JS 로 재구현)
  - 지원 조건: `ta.crossover` · `ta.crossunder`
  - 지원 입력: `input.float(...)` (`/100` 표기 감지)
  - 진입/청산 감지: `strategy.entry(..., strategy.long)` · `strategy.close` 앞 2줄 안에
    참인 조건 변수가 등장하면 신호로 판정
- **내장 예제 3종**: 이동평균 교차 / 3% 익절·1.5% 손절 / RSI 반전
- **익절·손절 시각화**: `strategy.exit` + 보유 포지션이 있으면 평단 기준 익절가·손절가를 계산하고,
  최신 봉의 고가/저가가 그 선에 닿았는지로 신호를 뒤집는다.
- **주문은 서버 권위**: 파싱·신호 생성은 브라우저에서 하되 체결은 서버가 하고
  `source="PINE"` 라벨을 붙여 **수동 웹 주문과 섞이지 않게** 한다. (코드 주석에 이 의도가 명시됨)
- 매도 신호 시 보유 수량을 수량 입력칸에 자동 채움.

| **구현 파일** | `ai_sheet.py`(126줄) · `frontend/js/ai-sheet.js` |

**동작 상세**
- URL 을 입력하면 그 페이지의 **표를 추출해 편집 가능한 스프레드시트**로 만든다.
  표가 없으면 20자 이상 문단들을 "순번·본문" 2열로 대신 채운다.
- **SSRF 방어가 꼼꼼하다** — 이 기능의 핵심:
  - scheme 은 http/https 만, port 는 80/443 만, URL 에 user/password 있으면 거부
  - `getaddrinfo` 로 **모든 A/AAAA 레코드가 global 주소인지** 검증 (사설망·루프백 차단)
  - **리디렉션 후 최종 URL 도 재검증**
  - Content-Type 에 `html` 없으면 415, 2MB 초과면 413
  - 최대 100행 × 20열, 셀당 500자, 문단당 1000자
- 파서는 표준 `html.parser` 자체 구현(외부 라이브러리 없음). 가장 셀이 많은 표를 선택.
- 프론트: 헤더·셀 인라인 편집 · 행 추가 · **CSV 다운로드**(BOM 포함 → Excel 한글 정상)

> **이름과 실제가 다르다**: "AI Sheet"지만 **AI/LLM 을 전혀 쓰지 않는다.** 규칙 기반 HTML 표 추출기다.

**v2.0 분류**

| 기능 | 구현 | 근거 |
|---|---|---|
| **살림** | **포팅** | SSRF 방어 로직은 그대로 옮길 가치가 크다(직접 다시 짜면 실수하기 쉬운 영역). 다만 **대회 도메인과의 관련성이 가장 약한 기능**이라 v2.0 1차 릴리스 범위에 넣을지는 별도 판단이 필요하다. |
