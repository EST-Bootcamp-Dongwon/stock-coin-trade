# 인덱스 · 쿼리 전략

> **문서 버전** v2.0 · **작성일** 2026-08-13 (KST) · **상위** [00-통합-ERD](00-통합-ERD.md)

**인덱스는 "있으면 좋은 것"이 아니라 조회 패턴 하나에 대응하는 것**이다.
이 문서는 **화면·잡별 실제 쿼리**를 먼저 적고, 그것을 받는 인덱스를 짝지어 둔다.
쓰지 않는 인덱스는 쓰기 비용만 늘리므로 만들지 않는다.

---

## 1. 원칙 4가지

| # | 원칙 |
|---|---|
| 1 | **쿼리 없는 인덱스는 만들지 않는다.** 이 문서에 쿼리가 적히지 않은 인덱스는 지운다 |
| 2 | **복합 인덱스는 등호 조건 → 정렬 순서**로 배치한다 |
| 3 | **부분 인덱스**(`condition=`)를 적극 쓴다. 미체결 주문은 전체의 1% 미만이다 |
| 4 | **랭킹·홈 화면은 외부 API 를 절대 호출하지 않는다.** 스냅샷·캐시만 읽는다 |

## 2. 화면별 쿼리와 인덱스

### 2.1 대회 랭킹 (`/contests/<slug>/ranking/`)

**가장 많이 열리는 대회 화면이다.**

```sql
SELECT participation_id, rank, prev_rank, nav, cumulative_return_pct,
       position_count, invested_ratio_pct
  FROM contest_ranking
 WHERE contest_id = %s AND date = %s
 ORDER BY rank NULLS LAST;
```

| 인덱스 | `contest_ranking (contest_id, date, rank)` |
|---|---|
| 왜 | 등호 2개 + 정렬 1개. **인덱스만으로 정렬이 끝난다**(Sort 노드 없음) |
| 행 수 | 참가자 100명 = 100행 |
| 금지 | `DailySnapshot` 조인 금지 — JSONB 3칸이 딸린 넓은 행을 100개 끌어온다 |

**`ContestRanking` 이 `DailySnapshot` 의 값을 일부 복제하는 이유가 이것이다**
(→ [E-02](E-02-contests.md) 8.1).

### 2.2 Top Pick 매트릭스 (종목 × 참가자) ★

**이 화면 때문에 `SnapshotHolding` 을 정규화했다.**

```sql
-- ① 수익률 상위 참가자 30명
SELECT participation_id FROM contest_ranking
 WHERE contest_id = %s AND date = %s AND rank IS NOT NULL
 ORDER BY rank LIMIT 30;

-- ② 그들의 종목별 비중
SELECT symbol, participation_id, weight_pct
  FROM snapshot_holding
 WHERE contest_id = %s AND date = %s
   AND participation_id = ANY(%s);
```

| 인덱스 | `snapshot_holding (contest_id, date, symbol)` |
|---|---|
| 왜 | 대회 + 날짜로 좁히면 **한 대회의 하루치 = 1,500행**. 그 안에서 필터 |
| JSONB 였다면 | `jsonb_to_recordset` 으로 2,000행을 매번 펼쳐야 하고 인덱스를 못 탄다 |

**행 수를 다시 확인**: 100명 × 15종목 × 20일 = 3만 행. 인덱스 없이도 도는 규모지만,
날짜별 조회가 반복되므로 걸어 둔다.

### 2.3 참가자 포트폴리오 상세 모달

```sql
-- 보유 종목 (그날 기준)
SELECT * FROM snapshot_holding
 WHERE participation_id = %s AND date = %s ORDER BY weight_pct DESC;

-- 종목별 시계열 ("이 사람이 이 종목을 언제부터 들고 있었나")
SELECT date, qty, weight_pct, pnl FROM snapshot_holding
 WHERE participation_id = %s AND symbol = %s ORDER BY date;
```

| 인덱스 | `snapshot_holding (participation_id, symbol, date)` |
|---|---|
| 주의 | 첫 쿼리는 `symbol` 을 건너뛰므로 이 인덱스의 선행 컬럼만 쓴다. 그래도 참가자 1명으로 좁혀지면 300행이라 충분하다 |

### 2.4 거래 이력 (`/orders/`)

```sql
SELECT * FROM "order"
 WHERE account_id = %s
   AND (asset_class = %s)      -- 선택
   AND (side = %s)             -- 선택
   AND created_at BETWEEN %s AND %s
 ORDER BY created_at DESC
 LIMIT 50 OFFSET %s;
```

| 인덱스 | 용도 |
|---|---|
| `order (account_id, created_at DESC)` | **기본 경로.** 필터 없이 최신순 |
| `order (account_id, asset_class, side)` | 자산군·매매구분 필터가 걸린 경우 |

> **`OFFSET` 페이지네이션의 한계** — 뒤쪽 페이지로 갈수록 느려진다.
> 대회 1달이면 참가자당 수백 건이라 문제가 되지 않는다.
> 그 이상 쌓이면 `created_at` 커서 방식으로 바꾼다(v2.1).

**`"order"` 는 따옴표가 필요하다** — SQL 예약어다(→ [E-03](E-03-trading.md) 4.3).

### 2.5 계좌 스냅샷 (`/portfolio/<id>/`)

```sql
-- 포지션 + 시세를 한 번에
SELECT p.symbol, p.qty, p.avg_price, p.principal,
       q.price, q.change_pct, q.is_simulated,
       s.name, s.sector_name
  FROM position p
  LEFT JOIN quote_cache  q ON q.symbol = p.symbol AND q.asset_class = p.asset_class
  LEFT JOIN stock_master s ON s.symbol = p.symbol
 WHERE p.account_id = %s;
```

| 인덱스 | `position (account_id)` — 유니크 제약이 이미 만든다 |
|---|---|
| 조인 | `quote_cache (asset_class, symbol)` UNIQUE · `stock_master` PK |
| 행 수 | 계좌당 15종목 |

**`LEFT JOIN` 인 이유**: 캐시가 없거나 대체자산이라 `StockMaster` 에 없어도
포지션 행은 나와야 한다. `INNER JOIN` 이면 종목이 조용히 사라진다.

### 2.6 홈 — 내 대회 현황

```sql
SELECT r.rank, r.prev_rank, r.nav, r.cumulative_return_pct, r.invested_ratio_pct,
       w.turnover_pct, w.is_violation
  FROM contest_ranking r
  LEFT JOIN weekly_turnover w
         ON w.participation_id = r.participation_id AND w.week_start = %s
 WHERE r.participation_id = %s AND r.date = %s;
```

**계산이 하나도 없다.** 미리 쌓아둔 두 행을 읽을 뿐이다.
v1.0 홈이 30초마다 전 종목 시세를 폴링하던 것과 대비된다.

## 3. 잡별 쿼리와 인덱스

### 3.1 `match_pending_orders` (장중 5초) — 가장 자주 도는 쿼리 ★

```sql
SELECT o.* FROM "order" o
 WHERE o.status IN ('ACCEPTED', 'PARTIAL')
   AND o.symbol = ANY(%s);          -- 방금 시세가 갱신된 종목들
```

| 인덱스 | **부분 인덱스** `order (symbol, status) WHERE status IN ('ACCEPTED','PARTIAL','PENDING_OPEN')` |
|---|---|
| 왜 부분인가 | 대회가 끝나면 주문 2만 건 중 **미체결은 0건**이다. 전체 인덱스는 99%가 죽은 행 |
| 크기 | 장중 미체결이 많아야 수백 건. 인덱스가 메모리에 통째로 올라온다 |

```python
models.Index(
    fields=["symbol", "status"],
    name="order_idx_open",
    condition=models.Q(status__in=["ACCEPTED", "PARTIAL", "PENDING_OPEN"]),
)
```

> **Django 관점** — SQLAlchemy 에서는 `Index(..., postgresql_where=...)` 였다.
> Django 는 `condition=Q(...)` 다. **부분 인덱스는 Postgres 전용**이라
> v1.0 의 MySQL 에서는 쓸 수 없던 기법이다. 엔진을 바꾸며 얻는 이득 중 하나다.

### 3.2 `poll_quotes` — 폴링 대상 선정

```sql
SELECT asset_class, symbol FROM subscription_registry
 WHERE expires_at > now()
 ORDER BY priority, last_polled_at NULLS FIRST
 LIMIT %s;                          -- 이번 창의 예산만큼
```

| 인덱스 | `subscription_registry (priority, last_polled_at)` |
|---|---|
| 의미 | "우선순위 높고 가장 오래 안 본 것부터". KIS 초당 5건 예산 안에서 공평하게 돈다 |

### 3.3 `settle_daily` — 일별 정산

```sql
-- 대상: 진행 중 대회의 승인 참가자
SELECT p.id, p.account_id FROM participation p
  JOIN contest c ON c.id = p.contest_id
 WHERE c.status = 'ONGOING' AND p.status = 'APPROVED';
```

| 인덱스 | `contest (status, start_date)` · `participation (contest_id, status)` |
|---|---|
| 쓰기 | `DailySnapshot` upsert 100행 → `SnapshotHolding` 1,500행 삭제 후 재삽입 |

**쓰기가 하루 한 번뿐이라 인덱스가 많아도 부담이 없다.**
반대로 `Order` 는 장중 내내 쓰이므로 인덱스를 최소로 유지한다.

### 3.4 규칙 검증 (주문마다) ★

주문 한 건마다 도는 쿼리다. **여기가 느리면 주문 UX 가 전부 느려진다.**

```sql
-- ① 종목 판정
SELECT * FROM stock_master WHERE symbol = %s;                    -- PK

-- ② 대회 유니버스(업종 고정값)
SELECT sector_code FROM contest_universe
 WHERE contest_id = %s AND symbol = %s;                          -- UNIQUE

-- ③ 현재 포지션 전체 (비중 계산)
SELECT symbol, qty, avg_price FROM position WHERE account_id = %s;

-- ④ 섹터 한도
SELECT sector_code, limit_pct FROM contest_sector_weight WHERE contest_id = %s;
```

**전부 PK 또는 유니크 인덱스 조회다.** 4번의 왕복이지만 각각 1ms 미만이고,
`select_related` 로 ②④를 미리 캐시하면 요청당 2회로 줄어든다.

> **`ContestSectorWeight.limit_pct` 를 미리 계산해 저장한 이유**가 여기서 드러난다.
> 주문마다 `rule_set` 을 파싱해 `max(비중×2, 10)` 을 다시 계산하면
> JSON 파싱 비용이 주문 경로에 들어온다.

## 5. 벡터 검색 — HNSW

```sql
SELECT id, title, category, content,
       1 - (embedding <=> %s::vector) AS similarity
  FROM knowledge_document
 WHERE is_approved = true AND embedding IS NOT NULL
 ORDER BY embedding <=> %s::vector
 LIMIT 5;
```

| 항목 | |
|---|---|
| 연산자 | `<=>` **코사인 거리** — v1.0 Qdrant 와 같은 기준 |
| 인덱스 | HNSW `vector_cosine_ops` (`m=16, ef_construction=64`) |
| 주의 | **`ORDER BY` 의 연산자가 인덱스 opclass 와 같아야** 인덱스를 탄다. `<->`(L2)로 쓰면 조용히 순차 스캔이 된다 |

문서가 21건뿐이라 지금은 순차 스캔이 더 빠르다. **그래도 인덱스를 만드는 이유**는
사용자 추가 문서가 쌓였을 때 조용히 느려지는 것을 막기 위해서다.

## 6. N+1 을 막는 자리 ★

Django ORM 에서 가장 흔한 성능 사고다. **어디서 나는지가 정해져 있다.**

| 화면 | 위험 | 처방 |
|---|---|---|
| 랭킹 목록 | 행마다 `participation.nickname` 접근 → 100회 쿼리 | `select_related("participation")` |
| 거래 이력 | 행마다 `order.account.contest.name` → 3중 조인 × 50 | `select_related("account__contest")` |
| 계좌 요약 | 계좌마다 포지션 조회 → 4회 | `prefetch_related("positions")` |
| Top Pick | 셀마다 종목명 조회 | `StockMaster` 를 한 번에 dict 로 읽어 메모리 조인 |

```python
# 랭킹 — 조인 1회로 끝난다
rows = (ContestRanking.objects
        .filter(contest=contest, date=d)
        .select_related("participation")           # ← 없으면 100번 쿼리
        .order_by(F("rank").asc(nulls_last=True)))
```

> **Django 관점** — SQLAlchemy 는 기본이 lazy 라 `joinedload()` 를 붙였다.
> Django 도 기본이 lazy 이고 `select_related`(FK, JOIN) / `prefetch_related`(역참조, 별도 쿼리)로 나뉜다.
> **어느 쪽인지 헷갈리면 `django-debug-toolbar` 로 쿼리 수를 세는 게 가장 빠르다.**

## 7. 만들지 않는 것

| 안 만드는 것 | 이유 |
|---|---|
| `Order.symbol` 단독 인덱스 | 부분 인덱스 `(symbol, status)` 가 대신한다 |
| `DailySnapshot.holdings` GIN 인덱스 | JSONB 는 감사 원본이고 **조회는 `SnapshotHolding` 이 받는다** |
| 파티셔닝 | 최대 테이블이 3만 행이다 |
| `Member.email` 추가 인덱스 | UNIQUE 제약이 이미 인덱스다 |
| 캐시 테이블의 `fetched_at` 인덱스 | 조회 조건은 항상 `expires_at` 이다 |

## 8. 착수 후 확인 절차

인덱스 설계는 **실측 전까지 가설**이다. 구현 착수 시 확인한다.

```sql
-- ① 쓰이지 않는 인덱스 찾기 (운영 1주 후)
SELECT relname, indexrelname, idx_scan
  FROM pg_stat_user_indexes
 WHERE idx_scan = 0 ORDER BY relname;

-- ② 느린 쿼리
EXPLAIN (ANALYZE, BUFFERS) <쿼리>;
```

**`idx_scan = 0` 인 인덱스는 지운다.** 이 문서에 쿼리를 적어두었으므로
"왜 만들었는지 모르겠다"는 상황이 생기지 않는다.
