## 1. 되돌릴 수 없는 두 가지 ★

착수 전에 **반드시** 정해야 한다. 나중에 바꾸려면 사실상 재구축이다.

| # | 항목 | 값 | 왜 되돌릴 수 없나 |
|---|---|---|---|
| 1 | **`AUTH_USER_MODEL`** | `"accounts.Member"` | 첫 `migrate` 이후에 바꾸면 모든 FK 가 깨진다 |
| 2 | **`DEFAULT_AUTO_FIELD`** | `"django.db.models.BigAutoField"` | 나중에 바꾸면 전 테이블 PK 마이그레이션이 생긴다 |

```python
# config/settings.py — 첫 makemigrations 전에 박아둔다
AUTH_USER_MODEL = "accounts.Member"
DEFAULT_AUTO_FIELD = "django.db.models.BigAutoField"

USE_TZ = True
TIME_ZONE = "Asia/Seoul"
```

> **Django 관점** — FastAPI 였다면 사용자 모델도 그냥 테이블 하나라 언제든 바꿀 수 있었다.
> Django 는 `auth` · `admin` · `sessions` 가 전부 `AUTH_USER_MODEL` 을 참조하므로
> **첫 마이그레이션 시점에 고정된다.** 이 한 줄이 이 프로젝트에서 가장 비싼 한 줄이다.

## 2. Postgres 확장 먼저

`pgvector` 와 `pg_cron` 은 **테이블보다 먼저** 있어야 한다.

```python
# insight/migrations/0001_initial.py
from django.db import migrations
from pgvector.django import VectorExtension


class Migration(migrations.Migration):
    initial = True
    operations = [
        VectorExtension(),        # CREATE EXTENSION IF NOT EXISTS vector
        # ... 이어서 KnowledgeDocument 생성
    ]
```

| 확장 | 설치 | 비고 |
|---|---|---|
| `vector` | **마이그레이션에서** | `VectorExtension()` 오퍼레이션 |
| `pg_cron` | **Supabase 대시보드에서 수동** | 마이그레이션으로 못 켠다(슈퍼유저 권한) |

### 2.1 착수 시 확인할 것 → **확인 완료 (2026-08-13)** ✅

```sql
-- pg_cron 버전 — 초 단위 스케줄 지원 여부가 갈린다
SELECT name, default_version, installed_version
  FROM pg_available_extensions WHERE name IN ('pg_cron', 'vector');
```

| 확장 | 설치 버전 | 판정 |
|---|---|---|
| `pg_cron` | **1.6.4** | **초 단위 지원** — 5초/10초 스케줄 실측 통과 |
| `vector` | 0.8.2 (로컬 `pgvector:pg16` 은 0.8.6) | 정상 |

**→ [F-20](../../features/version2.0/F-20-스케줄러.md) 4.2 폴백안은 폐기했다.**
시세 폴링(우선순위 1 = 5초)을 pg_cron 으로 직접 돌린다.

## 3. 앱 생성과 마이그레이션 순서

### 3.1 의존 순서

```
1. core        ← 추상 모델·상수만. 테이블 3개
2. market      ← 다른 앱을 참조하지 않는다
3. accounts    ← Member(AUTH_USER_MODEL) · Account(contest 는 나중에)
4. contests    ← accounts 참조
5. accounts    ← Account.contest FK 추가 (순환 해소용 2단계) ★
6. trading     ← accounts 참조
7. learning · insight   ← accounts 참조
```

### 3.2 순환 참조를 2단계로 푸는 이유 ★

`accounts.Account.contest` → `contests.Contest` 이고
`contests.Participation.account` → `accounts.Account` 다.

**문자열 참조를 써도 마이그레이션 그래프에서는 순환이 될 수 있다.**
Django 는 대부분 자동으로 풀지만, 실패하면 이렇게 나눈다.

```python
# accounts/migrations/0001_initial.py — Account 를 contest 없이 만든다
# contests/migrations/0001_initial.py — Contest·Participation 생성
# accounts/migrations/0002_account_contest.py — FK 추가
class Migration(migrations.Migration):
    dependencies = [("accounts", "0001_initial"), ("contests", "0001_initial")]
    operations = [
        migrations.AddField(
            model_name="account",
            name="contest",
            field=models.ForeignKey(null=True, blank=True, to="contests.contest",
                                    on_delete=django.db.models.deletion.PROTECT,
                                    related_name="accounts"),
        ),
    ]
```

> **먼저 그냥 해 본다.** `makemigrations` 가 알아서 순서를 잡으면 2단계가 필요 없다.
> `CircularDependencyError` 가 났을 때만 위 방법을 쓴다.

### 3.3 실행

```bash
python manage.py makemigrations core market accounts contests trading learning insight
python manage.py migrate
```

**앱 이름을 명시적으로 나열한다.** 인자 없이 돌리면 순서가 뒤섞여 보이기 어렵다.

## 5. 시드 데이터

**세 종류를 명확히 구분한다.**

| 종류 | 방법 | 운영 환경 |
|---|---|---|
| **필수 기준 데이터** | 데이터 마이그레이션 | **들어간다** |
| **운영 초기 데이터** | management command | 운영자가 1회 실행 |
| **데모·테스트 데이터** | `seed_demo` command | **들어가지 않는다** |

### 5.1 필수 기준 데이터 (마이그레이션)

없으면 서비스가 동작하지 않는 것들이다.

> **2026-08-13 갱신 — 전부 구현·검증 완료.** 되돌리기 왕복까지 확인했다.

| 대상 | 내용 | 마이그레이션 |
|---|---|---|
| 권한 그룹 | `contest_admin`(23권한) · `content_admin`(10권한) (→ [F-19](../../features/version2.0/F-19-관리자.md) 4장) | `accounts/0004` |
| `AlternativeProduct` | **11종** — v1.0 하드코딩 이관 (→ [E-03](E-03-trading.md) 7장) | `trading/0003` |
| `KnowledgeDocument` | **시드 21건** — `source="SEED"`, `is_approved=True`, `embedding=NULL` | `insight/0002` |
| `Lesson` | **13레슨**(명세는 14 — 변경노트 E-12) · `Guide` 4종 | `learning/0002` |
| `AppSetting` | 기본 설정값 12건 | `core/0002` |

#### 권한 그룹의 함정 — `Permission` 은 아직 없다 ★★

Django 는 `Permission` 을 **마이그레이션으로 만들지 않는다.** `post_migrate`
시그널이 만드는데, 그건 **모든 마이그레이션이 끝난 뒤**에 발화한다.

```
migrate ─┬─ 0001_initial ...
         ├─ 0004_seed_permission_groups   ← 여기서 Permission 을 찾으면 0건
         └─ (전부 끝) → post_migrate → create_permissions() 가 그제야 만든다
```

빈 DB 에 `migrate` 를 돌리면 **그룹은 생기지만 권한이 하나도 안 붙는다.**
게다가 조용히 성공한다. 그래서 시드 마이그레이션이 `create_permissions()` 를
**직접 먼저 호출**한다. 멱등이라 두 번 불려도 안전하다.

찾지 못한 권한이 하나라도 있으면 `RuntimeError` 로 **즉시 실패시킨다** —
모델명 오타로 권한이 조용히 빠지는 것을 배포 후에 발견하는 것보다 낫다.

```python
# trading/migrations/0002_seed_alternative_products.py
def seed_products(apps, schema_editor):
    """대체자산 11종. v1.0 은 파이썬 상수였다.

    Django 관점 — 데이터 마이그레이션에서는 반드시 apps.get_model() 로 모델을 얻는다.
    직접 import 하면 "그 시점의 모델"이 아니라 "현재 코드의 모델"을 쓰게 되어,
    나중에 필드를 추가하면 과거 마이그레이션이 깨진다.
    """
    AlternativeProduct = apps.get_model("trading", "AlternativeProduct")
    AlternativeProduct.objects.bulk_create([...], ignore_conflicts=True)


def unseed(apps, schema_editor):
    apps.get_model("trading", "AlternativeProduct").objects.all().delete()


class Migration(migrations.Migration):
    dependencies = [("trading", "0001_initial")]
    operations = [migrations.RunPython(seed_products, unseed)]
```

**되돌리기(`unseed`)를 반드시 짝으로 넣는다.** 없으면 `migrate <app> <이전번호>` 가 실패한다.

### 5.2 임베딩은 마이그레이션에서 만들지 않는다 ★

시드 지식 21건의 **벡터는 마이그레이션에서 계산하지 않는다.**

| 이유 | |
|---|---|
| fastembed 모델 로드가 수십 초~수 분 | 배포 파이프라인이 멈춘다 |
| 마이그레이션이 무거워지면 롤백도 어렵다 | |

**문서만 넣고 `embedding = NULL` 로 둔다.** 배치 잡이 나중에 채운다
(→ [E-06](E-06-insight.md) 2.5). 벡터가 없는 문서는 검색에 안 나오므로 안전하다.

```bash
python manage.py backfill_embeddings          # 착수 시 1회 수동 실행
```

#### ★★ KRX 계정이 필요하다 — 착수 전 준비물 (변경노트 E-16)

**2026-08-13 확인 — `data.krx.co.kr` 이 로그인을 요구하도록 바뀌었다.**
자격증명이 없으면 pykrx 의 모든 호출이 `LOGOUT`(HTTP 400) 으로 실패한다.

```env
# backend/.env  — 변수명은 KRX_PASSWORD 가 아니라 **KRX_PW** 다 (pykrx 가 읽는 이름)
KRX_ID=...
KRX_PW=...
```

무료 회원가입이면 된다. 업비트·임베딩 커맨드는 자격증명 없이 동작한다.

#### 공통 옵션

| 옵션 | 뜻 |
|---|---|
| `--dry-run` | 외부 데이터는 받되 DB 에 쓰지 않는다. **배치 이력도 남기지 않는다** |
| `--soft-fail` | 외부 장애를 경고로 낮추고 종료 코드 0. 배포 스크립트·스케줄러용 |
| `--triggered-by` | `DataSyncLog` 에 남길 실행 주체 (`CLI` 기본 / `CRON` / `ADMIN`) |

**로직은 `services.py` 에 있고 커맨드는 껍데기다** — [F-16](../../features/version2.0/F-16-시장데이터-파이프라인.md) 5.3 이
요구한 구조다. pg_cron 이 HTTP 로 부르는 잡과 CLI 가 **같은 함수**를 쓴다.

## 6. `ensure_tables()` 를 쓰지 않는다

v1.0 은 앱 기동 시 `CREATE TABLE IF NOT EXISTS` 를 실행했다.
"재배포만으로 새 기능이 동작"하는 영리한 장치였지만 Django 에서는 **금지**한다.

| 문제 | |
|---|---|
| 스키마 권위가 둘이 된다 | 마이그레이션과 런타임 DDL |
| `AppConfig.ready()` 는 `manage.py` 커맨드에서도 호출된다 | 마이그레이션 중에 테이블을 만드는 사고 |
| 변경 이력이 없다 | 롤백 불가 |

**같은 이유로 `AppConfig.ready()` 에 스케줄러를 붙이지 않는다**
(→ [F-20](../../features/version2.0/F-20-스케줄러.md) 1장).

## 8. 로컬 개발 DB

| 환경 | DB |
|---|---|
| **로컬** | Docker Compose 의 `postgres:16` + `pgvector` 이미지 |
| **운영** | Supabase |

**로컬도 Postgres 를 쓴다.** SQLite 로 개발하면 부분 유니크 인덱스·`vector` 타입·
`ON CONFLICT` 동작이 달라 **로컬에서 통과한 것이 운영에서 깨진다.**

```yaml
# docker-compose.yml (발췌)
services:
  db:
    image: pgvector/pgvector:pg16      # pgvector 가 미리 들어 있는 공식 이미지
    environment:
      POSTGRES_DB: stockcoin
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    ports: ["5432:5432"]
```

`pg_cron` 은 로컬에 없어도 된다 — 잡은 **management command 로 직접 실행**해 개발한다.
이것이 [F-16](../../features/version2.0/F-16-시장데이터-파이프라인.md) 5.3 에서
"HTTP 엔드포인트와 CLI 커맨드 양쪽에서 재사용하도록 서비스 함수로 분리"한 이유다.
