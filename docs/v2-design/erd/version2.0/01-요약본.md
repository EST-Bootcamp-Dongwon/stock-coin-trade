## 핵심 설계 5가지

### 1. `Account` — 조건부 유니크 ★

```
연습 계좌: UNIQUE(member, mode)    WHERE contest IS NULL
대회 계좌: UNIQUE(member, contest) WHERE contest IS NOT NULL
```

**조건 없이 걸면 `NULL != NULL` 규칙 때문에 연습 계좌가 무제한 생긴다.**
이 부분 인덱스가 v1.0 결함 D-5(계좌 초기화가 코인을 안 지움)를 구조적으로 없앤다.

### 2. `Order` — 자산군 통합 (결함 D-4)

`stock_order` + `alternative_order` + **(없던 코인)** → `Order(asset_class=…)`

> **주의**: v1.0 의 `order_type` 은 **매수/매도**였다. v2.0 에서는 `side` 다.
> v2.0 의 `order_type` 은 **가격 유형**(시장가/지정가/상대호가/자기호가/STOP)이다.

### 3. 스냅샷 이중 저장

| | 역할 |
|---|---|
| `DailySnapshot.holdings` (jsonb) | **감사용 원본 · 정본** |
| `SnapshotHolding` (3만 행) | **Top Pick 매트릭스 · 수익종목 집계** |

정합성 규약: **같은 트랜잭션 · JSONB 가 정본 · 재생성 커맨드 보유.**

### 4. 종목은 FK 가 아니라 문자열

주식·코인·대체자산이 한 컬럼(`symbol`)에 오고, 상장폐지가 이력을 막으면 안 된다.
**대신 주문 접수 시 `StockMaster` 조회를 필수 단계로 둔다.**

### 5. 캐시는 전부 테이블 (결함 D-9)

`QuoteCache` · `OrderbookCache` · `ChartCache` · `IndexCache` · `NewsCache` +
`ApiCallBudget`(KIS 초당 5건 전역 예산) · `RateLimitCounter`.

**요청을 넘어서 사는 프로세스 메모리 캐시는 만들지 않는다.**

## 인덱스 — 쿼리 3개가 설계를 결정한다

| 쿼리 | 인덱스 |
|---|---|
| 랭킹 목록 | `contest_ranking (contest, date, rank)` — 정렬까지 인덱스가 끝낸다 |
| **Top Pick 매트릭스** | `snapshot_holding (contest, date, symbol)` |
| **미체결 체결 추종** (5초) | **부분** `order (symbol, status) WHERE status IN (…)` |

부분 인덱스는 **Postgres 전용**이다. v1.0 의 MySQL 에서는 쓸 수 없던 기법이다.
