> **문서 버전** v2.0 · **작성일** 2026-08-13 (KST) · **상위** [00-통합-ERD](00-통합-ERD.md)

## 1. 앱 분할 (확정) ★

사용자 확정: **도메인별 7개.**

| 앱 | 책임 | 모델 수 | 대표 모델 |
|---|---|---|---|
| `accounts` | 회원 · 계좌 · API 키 · 관심종목 | 5 | `Member` · `Account` |
| `contests` | 대회 · 참가 · 스냅샷 · 랭킹 · 정산 · 위반 | 11 | `Contest` · `DailySnapshot` |
| `trading` | 주문 · 체결 · 포지션 · 대체자산 상품 | 5 | `Order` · `Position` |
| `market` | 종목 마스터 · 영업일 · 시세 캐시 · 외부 토큰 | 13 | `StockMaster` · `QuoteCache` |
| `learning` | 레슨 · 진행률 · 가이드 | 3 | `Lesson` · `LearningProgress` |
| `insight` | AI · RAG 지식 · 도구(수집기) | 4 | `KnowledgeDocument` |
| `core` | 배치 이력 · 감사 로그 · 설정 · 공통 추상모델 | 3 | `DataSyncLog` · `AdminAuditLog` |

**합계 44개 모델.**

### 1.1 의존 방향 — 순환 참조 금지 ★

```
core  ◀── 모두가 참조 (추상 모델만 제공. 역참조 없음)
  ▲
market ◀── trading ◀── contests ◀── accounts
                              ▲          │
                              └──────────┘   ← 여기만 양방향
learning · insight ── accounts 만 참조
```

**딱 한 곳에서 순환이 생긴다.**

- `accounts.Account.contest` → `contests.Contest`
- `contests.Participation.account` → `accounts.Account`

Django 에서 이건 **문자열 참조**로 푼다.

```python
# accounts/models.py
class Account(models.Model):
    contest = models.ForeignKey(
        "contests.Contest",          # ← import 하지 않고 "앱라벨.모델명" 문자열로 쓴다
        null=True, blank=True,
        on_delete=models.PROTECT,
        related_name="accounts",
    )
```

> **Django 관점** — FastAPI + SQLAlchemy 에서는 `relationship("Contest")` 문자열 참조와
> `TYPE_CHECKING` 임포트를 섞어 쓰는 게 보통이었다. Django 는 **문자열 참조가 정식 방법**이고
> 마이그레이션도 이걸 그대로 해석한다. 순환 임포트를 걱정할 필요가 없다.
> 대신 **앱 라벨을 오타 내면 `makemigrations` 시점에야 터진다.**

## 2. 값 타입 규약 ★

**이 표가 이 문서에서 가장 중요하다.** 자산군이 통합된 테이블(`Order` · `Position`)에서
주식(정수 수량)과 코인(소수점 8자리)이 한 칸을 같이 쓰기 때문이다.

| 종류 | Django 필드 | Postgres | 근거 |
|---|---|---|---|
| **원화 금액** | `BigIntegerField` | `bigint` | 수수료·세금을 **원 단위 floor 절사**하기로 확정([F-03](../../features/version2.0/F-03-주문-체결엔진.md) 6장). 소수 원이 생기지 않는다 |
| **수량** | `DecimalField(28, 8)` | `numeric(28,8)` | 주식은 정수값이 들어가고, **코인이 소수점 8자리**를 쓴다. 통합 테이블이라 넓은 쪽에 맞춘다 |
| **단가** | `DecimalField(20, 8)` | `numeric(20,8)` | 주식 원 단위 · 코인 소수 · 대체자산 원 단위를 모두 담는다 |
| **비율(%)** | `DecimalField(9, 4)` | `numeric(9,4)` | `-99999.9999` ~ `99999.9999`. 수익률이 4자리를 넘는 경우는 없다 |
| **bp(베이시스포인트)** | `PositiveSmallIntegerField` | `smallint` | `fee_bp = 10` 처럼 정수. 실수 오차가 끼지 않는다 |
| **시각** | `DateTimeField` | `timestamptz` | 아래 3장 |
| **날짜** | `DateField` | `date` | **KST 기준 영업일**. 아래 3.2 |
| **구조화 데이터** | `JSONField` | `jsonb` | `rule_set` · 스냅샷 원본 등 |
| **벡터** | `pgvector.django.VectorField(384)` | `vector(384)` | [F-15](../../features/version2.0/F-15-지식검색-RAG.md) |

### 2.1 반복을 줄이는 상수

같은 `max_digits` 를 44개 모델에 손으로 적으면 반드시 어긋난다.

```python
# core/fields.py
"""값 타입 규약을 한 곳에 모은다. 개별 모델은 여기서만 가져다 쓴다."""

# 수량 — 코인 소수점 8자리를 담아야 해서 넓게 잡는다
QTY = dict(max_digits=28, decimal_places=8)

# 단가 — 주식(원 단위)과 코인(소수)을 함께 담는다
PRICE = dict(max_digits=20, decimal_places=8)

# 비율(%) — 수익률·비중·회전율
PCT = dict(max_digits=9, decimal_places=4)
```

```python
# 사용 예
from core.fields import QTY, PRICE, PCT

qty        = models.DecimalField(**QTY, default=0, verbose_name="수량")
avg_price  = models.DecimalField(**PRICE, default=0, verbose_name="평균 단가")
weight_pct = models.DecimalField(**PCT, default=0, verbose_name="비중 %")
```

> **Django 관점** — 마이그레이션은 `QTY` 라는 이름이 아니라 **풀린 값**(`max_digits=28, ...`)을
> 기록한다. 나중에 `QTY` 를 바꾸면 그때 `makemigrations` 가 변경을 감지한다.
> FastAPI + Alembic 에서 타입 별칭을 쓰던 감각과 같다.

### 2.2 왜 금액을 `Decimal` 이 아니라 `BigInteger` 로 두는가

돈에 `float` 를 쓰면 안 된다는 건 상식이지만, `Decimal` 과 정수 중에서는 갈린다.

| | 판단 |
|---|---|
| **채택: `BigIntegerField`** | 원화는 최소 단위가 1원이고, [F-03](../../features/version2.0/F-03-주문-체결엔진.md) 6장이 **수수료·세금을 `floor` 절사**하기로 확정했다. 소수 원이 애초에 생기지 않는다 |
| 기각: `DecimalField` | 표현할 수 있는 소수부를 쓰지 않으면서 비교·집계 비용만 낸다 |

**단, 절사 잔차를 어디로 보낼지는 정해둬야 한다.**

매도 시 매수원금 차감은 `principal × (매도수량 / 보유수량)` 이라 소수가 나온다.

```
차감 원금 = floor(principal × 매도수량 / 보유수량)
→ 남은 수량이 0 이 되는 마지막 매도에서는 principal 을 통째로 0 으로 만든다
```

**마지막 매도에서 잔차를 청소한다.** 안 그러면 수량이 0인데 원금이 3원 남는 유령이 생긴다.

## 3. 시간 규약 ★

### 3.1 저장은 UTC, 표시는 KST

```python
# settings.py
USE_TZ = True                  # DB 에는 timestamptz 로, 내부적으로는 UTC 로 저장
TIME_ZONE = "Asia/Seoul"       # 템플릿·Admin 표시는 KST
```

- **모델·서비스 코드에서는 `django.utils.timezone.now()` 만 쓴다.**
  `datetime.now()` 는 naive 라 서버 로케일에 끌려간다.
- pg_cron 은 **UTC 로 동작**한다. 잡 등록 시 KST 를 환산해 적는다
  (→ [F-20](../../features/version2.0/F-20-스케줄러.md) 2장).

> **Django 관점** — FastAPI 에서는 `datetime` 을 어떻게 다룰지 프로젝트마다 달랐다.
> Django 는 `USE_TZ=True` 를 켜는 순간 **aware datetime 이 아닌 값을 넣으면 경고**를 띄운다.
> 강제성이 있어서 오히려 실수가 줄어든다.

### 3.2 `DateField` 는 전부 "KST 기준 영업일"이다

`DailySnapshot.date` · `TradingCalendar.date` · `WeeklyTurnover.week_start` 는
시각이 아니라 **한국 장의 하루**를 가리킨다.

UTC 로 환산하면 날짜가 하루 밀린다. **날짜를 만들 때 반드시 KST 로 변환한 뒤 `.date()` 를 취한다.**

```python
from django.utils import timezone
import zoneinfo

KST = zoneinfo.ZoneInfo("Asia/Seoul")

def today_kst():
    """오늘의 KST 날짜. 정산·스냅샷의 date 는 전부 이걸 쓴다."""
    return timezone.now().astimezone(KST).date()
```

### 3.3 주(week)의 시작

[F-04](../../features/version2.0/F-04-대회-규칙엔진.md) 5.1 확정 — **월요일 00:00 ~ 일요일 24:00 KST.**
`WeeklyTurnover.week_start` 에는 **그 주 월요일의 KST 날짜**를 넣는다.

## 4. 명명 규약

### 4.1 테이블명은 명시적으로 지정한다 ★

Django 는 기본적으로 테이블명을 `<앱라벨>_<모델명소문자>` 로 만든다
(`contests_dailysnapshot`). 우리는 **`db_table` 을 직접 지정**한다.

| 이유 | |
|---|---|
| **pg_cron 잡이 SQL 로 직접 접근한다** | 앱을 나중에 옮기면 테이블명이 바뀌어 잡이 조용히 깨진다 |
| Supabase 대시보드에서 사람이 읽는다 | `daily_snapshot` 이 `contests_dailysnapshot` 보다 낫다 |
| SQL 뷰·인덱스를 손으로 만들 일이 있다 | |

```python
class DailySnapshot(models.Model):
    ...
    class Meta:
        db_table = "daily_snapshot"      # ← 앱을 옮겨도 테이블명은 안 바뀐다
```

**규칙**: `snake_case` · **단수형** · 접두사 없음.

### 4.2 그 외

| 대상 | 규칙 | 예 |
|---|---|---|
| 모델 클래스 | `PascalCase` 단수 | `DailySnapshot` |
| 필드 | `snake_case` | `cumulative_return_pct` |
| 금액 필드 | `_amount` 또는 의미어 | `buy_amount` · `cash` |
| 비율 필드 | **`_pct` 접미사 필수** | `weight_pct` |
| 불리언 | `is_` / `has_` | `is_ranked` · `is_frozen` |
| 시각 | `_at` | `filled_at` |
| 날짜 | `_date` 또는 `date` | `start_date` |
| 선택지 클래스 | `models.TextChoices` | `OrderStatus` |
| 제약 이름 | `<테이블>_<의미>` | `account_uniq_practice_mode` |

**비율 필드에 `_pct` 를 강제하는 이유**: `0.15`(비율)와 `15.0`(퍼센트)를 섞는 사고가
금융 코드에서 가장 흔한 버그다. 이름으로 못을 박는다. **DB 에는 항상 퍼센트 값(15.0)을 넣는다.**

## 5. `on_delete` 정책 ★

Django 는 FK 마다 삭제 정책을 강제로 요구한다. 아무거나 고르면 안 된다.

| 정책 | 쓰는 곳 | 이유 |
|---|---|---|
| **`PROTECT`** | 회계·이력 성격 — `Order.account` · `Participation.member` · `Participation.contest` · `Account.member` | **지워지면 안 되는 것.** 참조가 남아 있으면 부모 삭제가 예외로 막힌다 |
| **`CASCADE`** | 소유 관계 — `Execution.order` · `SnapshotHolding.snapshot` · `Position.account` · `ContestUniverse.contest` | 부모가 사라지면 존재 의미가 없는 것 |
| **`SET_NULL`** | 선택적 참조 — `KnowledgeDocument.created_by` · `AvgDownSimulation.executed_order` | 참조 대상이 없어져도 본체는 남아야 하는 것 |
| `DO_NOTHING` | **쓰지 않는다** | 무결성이 DB 에만 남고 코드에서 안 보인다 |

### 5.1 회원 탈퇴는 삭제가 아니다 ★

`Member` 를 실제로 `DELETE` 하면 `PROTECT` 에 막혀 실패한다. **의도한 설계다.**

- 대회 순위·거래 이력은 **다른 참가자의 상대평가 근거**다. 한 명이 빠지면 순위가 흔들린다
- 탈퇴는 `is_active = False` + 개인정보 익명화로 처리한다
- 실격도 마찬가지다 — [F-02](../../features/version2.0/F-02-대회-도메인.md) 4.3 이
  **"계좌·주문 이력을 지우지 않는다"**를 이미 확정했다

> **Django 관점** — SQLAlchemy 는 `ondelete` 를 안 적으면 DB 기본값(보통 `NO ACTION`)으로
> 흘러간다. Django 는 **안 적으면 아예 에러**가 난다. 44개 모델에서 한 번씩 다 물어보므로
> 귀찮지만, "이 데이터가 지워져도 되는가"를 강제로 생각하게 만든다.

## 6. 제약(constraint) 규약

**"코드가 지키겠지"에 맡기지 않는다.** pg_cron 잡·Django Admin·Open API 가
같은 테이블을 서로 다른 경로로 건드리기 때문이다.

| 종류 | 예 | 쓰는 이유 |
|---|---|---|
| `UniqueConstraint` | `UNIQUE(participation, date)` | **정산 멱등성.** 두 번 돌아도 한 행 |
| **조건부 `UniqueConstraint`** | 연습 계좌는 모드당 1개(대회 계좌는 제외) | 아래 6.1 |
| `CheckConstraint` | `start_date <= end_date` · `qty >= 0` | 음수 수량 같은 물리적 불가능을 DB 가 막는다 |

### 6.1 조건부 유니크 — `Account` 의 예 ★

계좌 규칙이 모드에 따라 다르다.

- 연습 계좌: 회원당 **모드별 1개** (`contest` 가 `NULL`)
- 대회 계좌: 회원당 **대회별 1개** (`contest` 가 있음)

한 테이블에서 두 규칙이 공존하므로 **부분 인덱스(partial unique index)**가 필요하다.

```python
class Meta:
    constraints = [
        # 연습 계좌 — 회원당 모드별 1개 (contest 가 NULL 인 행만 대상)
        models.UniqueConstraint(
            fields=["member", "mode"],
            condition=models.Q(contest__isnull=True),
            name="account_uniq_practice_mode",
        ),
        # 대회 계좌 — 회원당 대회별 1개
        models.UniqueConstraint(
            fields=["member", "contest"],
            condition=models.Q(contest__isnull=False),
            name="account_uniq_contest",
        ),
    ]
```

> **Django 관점** — `unique_together` 로는 이게 안 된다. 조건을 붙일 수 없기 때문이다.
> `UniqueConstraint(condition=...)` 는 Postgres 의 `CREATE UNIQUE INDEX ... WHERE ...` 로
> 번역된다. `NULL` 은 서로 같지 않다고 보는 SQL 규칙 때문에 **조건 없이 걸면 연습 계좌가
> 무제한 생긴다.** 이 함정을 아는 게 중요하다.

## 7. 공통 추상 모델

44개 모델 중 대부분이 `created_at` / `updated_at` 을 갖는다. 추상 모델로 뺀다.

```python
# core/models.py
from django.db import models


class TimeStampedModel(models.Model):
    """생성·수정 시각을 자동 기록한다. 대부분의 모델이 이걸 상속한다.

    Django 관점 — abstract = True 면 이 클래스로는 테이블이 생기지 않고,
    상속한 자식 테이블에 컬럼만 복사된다. SQLAlchemy 의 declarative mixin 과 같은 역할이다.
    """

    created_at = models.DateTimeField(auto_now_add=True, verbose_name="생성 시각")
    updated_at = models.DateTimeField(auto_now=True, verbose_name="수정 시각")

    class Meta:
        abstract = True          # ← 이게 없으면 core_timestampedmodel 테이블이 진짜 생긴다
```

**캐시 테이블은 상속하지 않는다.** `fetched_at` / `expires_at` 이 이미 있고,
매 갱신마다 `updated_at` 을 함께 쓰는 것은 낭비다.

## 8. `TextChoices` — 상태값의 단일 정의처 ★

상태·구분값은 **전부 `models.TextChoices`** 로 정의한다.
문자열을 코드 여기저기 흩뿌리면 오타가 런타임까지 살아남는다.

```python
class OrderStatus(models.TextChoices):
    PENDING_OPEN = "PENDING_OPEN", "장 시작 대기"
    ACCEPTED     = "ACCEPTED",     "접수"
    PARTIAL      = "PARTIAL",      "부분체결"
    FILLED       = "FILLED",       "체결완료"
    CANCELLED    = "CANCELLED",    "취소"
    REJECTED     = "REJECTED",     "거부"
```

| 얻는 것 | |
|---|---|
| DB 값 | `"FILLED"` |
| 화면 표시명 | `order.get_status_display()` → `"체결완료"` |
| Django Admin | 드롭다운·필터가 자동 생성 |
| 코드 참조 | `OrderStatus.FILLED` — 오타가 나면 즉시 `AttributeError` |

**정의 위치**: 해당 앱의 `constants.py` 또는 `models.py` 상단.
여러 앱이 함께 쓰는 것(`AssetClass`)만 `core/constants.py` 에 둔다.

### 8.1 앱 경계를 넘는 공통 선택지

```python
# core/constants.py
class AssetClass(models.TextChoices):
    STOCK  = "STOCK",  "주식"
    CRYPTO = "CRYPTO", "코인"
    ALT    = "ALT",    "대체자산"


class AccountMode(models.TextChoices):
    CONTEST         = "CONTEST",         "대회"
    PRACTICE_STOCK  = "PRACTICE_STOCK",  "주식 연습"
    PRACTICE_CRYPTO = "PRACTICE_CRYPTO", "코인 연습"
    PRACTICE_ALT    = "PRACTICE_ALT",    "대체자산 연습"

    @property
    def asset_class(self) -> str:
        """모드 → 자산군 매핑. 계좌에 asset_class 컬럼을 따로 두지 않는 이유다."""
        return {
            self.CONTEST: AssetClass.STOCK,          # 1차는 주식 대회만
            self.PRACTICE_STOCK: AssetClass.STOCK,
            self.PRACTICE_CRYPTO: AssetClass.CRYPTO,
            self.PRACTICE_ALT: AssetClass.ALT,
        }[self]
```

> **`Account` 에 `asset_class` 컬럼을 두지 않는다.** 모드가 자산군을 결정하므로
> 컬럼으로 두면 둘이 어긋날 수 있다. 다만 **`Order` 에는 저장한다** — 이력 테이블이라
> 조회 필터가 잦고, 사후에 조인 없이 읽을 수 있어야 한다.

## 9. `select_for_update` 를 쓰는 자리 ★

동시성 사고가 날 수 있는 지점은 정해져 있다. 여기서만 행을 잠근다.

| 지점 | 잠그는 대상 | 근거 |
|---|---|---|
| 주문 체결 | `Account` (현금) + `Position` | [F-03](../../features/version2.0/F-03-주문-체결엔진.md) 7.1 |
| 시세 캐시 갱신 | `QuoteCache` / `OrderbookCache` — **`SKIP LOCKED`** | 같은 종목을 여러 요청이 동시에 갱신하지 않게 |
| KIS 유량 예산 | `ApiCallBudget` | [F-16](../../features/version2.0/F-16-시장데이터-파이프라인.md) 2.4 |

```python
from django.db import transaction

with transaction.atomic():                                   # ← 이 블록이 없으면 에러가 난다
    account = Account.objects.select_for_update().get(pk=account_id)
    # ... 잔고 검증 → 차감 → 포지션 갱신 → 주문 기록
```

> **Django 관점** — SQLAlchemy 의 `with_for_update=True` 와 같은 의도다.
> 차이는 **Django 는 `transaction.atomic()` 밖에서 부르면 `TransactionManagementError`**
> 를 던진다는 점이다. 실수로 잠금 없이 도는 경로가 생기지 않아 오히려 안전하다.

**Open API rate limit 은 잠그지 않는다.** `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`
한 방으로 원자적 처리가 가능하다 (→ [F-13](../../features/version2.0/F-13-OpenAPI.md) 3.2).

## 10. 캐시 테이블의 특수 규약

`market` 앱의 캐시 6종(`QuoteCache` 외)은 성격이 다르다.

| 규약 | 내용 |
|---|---|
| **`TimeStampedModel` 미상속** | `fetched_at` · `expires_at` 이 그 역할을 한다 |
| **FK 없음** | 캐시가 본 데이터를 붙잡고 있으면 정리가 어려워진다. `symbol` 문자열로만 참조 |
| **TTL 은 컬럼으로** | `expires_at > now()` 로 유효성 판정 (→ [F-16](../../features/version2.0/F-16-시장데이터-파이프라인.md) 2.3) |
| **upsert 전용** | `TRUNCATE` 후 재적재 금지. v1.0 `crypto_rank` 의 실수를 반복하지 않는다 |
| **정리 잡** | `cleanup`(매일 04:00)이 만료 행을 지운다 (→ [F-20](../../features/version2.0/F-20-스케줄러.md) 2장) |

## 11. 이 규약이 막는 v1.0 결함

| 규약 | 막는 결함 |
|---|---|
| 5장 `PROTECT` + 탈퇴는 비활성화 | 이력 소실 |
| 6장 조건부 유니크 | **D-5** — 계좌가 뒤섞여 초기화가 새는 문제 |
| 10장 캐시 테이블화 | **D-9** — 프로세스 메모리 캐시 |
| 8장 `TextChoices` | 상태 문자열 오타 |
| 2장 값 타입 통일 | 주식·코인이 한 테이블에 섞이는 문제(**D-4** 해소의 전제) |
