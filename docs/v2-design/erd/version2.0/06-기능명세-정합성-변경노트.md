### A-1. `MarketIndexSnapshot.nav` 는 저장할 수 없다 ★

| | |
|---|---|
| **명세** | [F-05](../../features/version2.0/F-05-랭킹-정산-스냅샷.md) 4.4 — `MarketIndexSnapshot(date, index_code, close, nav)` · "대회 시작일을 1000 으로 환산한 NAV 를 함께 기록" |
| **문제** | NAV 는 **대회 시작일**을 1000 으로 놓은 값인데, 이 테이블은 대회와 무관한 **전역 시계열**이다. 대회가 3개면 같은 날짜에 NAV 가 3개여야 한다. 한 행에 담을 수 없다 |

```
지수 NAV(대회 c, 날짜 d) = 1000 × close(d) / close(대회 c 의 시작일)
```

기준일 종가 1건만 더 읽으면 되고, 대회가 몇 개든 같은 테이블을 공유한다.
`MarketIndexSnapshot(date, index_code, close, change_pct)` 로 확정.

## B. 명세에 없던 필드 보강 (8건)

명세의 **요구를 만족하려면 필요한데** 모델 목록에는 없던 것들이다.
기능 자체를 바꾸지는 않는다.

### B-1. `Order.realized_pnl`

[F-10](../../features/version2.0/F-10-거래이력.md) 2.4 가 거래이력 상단에 **실현손익 합계**를 요구한다.
사후에 계산하려면 그 시점의 평단이 필요한데, **`Position` 은 현재 상태만 갖고 있어
과거 평단을 복원할 수 없다.** 매도 체결 시점에 기록하는 것이 유일하게 정확한 방법이다.

→ [E-03](E-03-trading.md) 4.4

### B-2. `Account.initial_capital`

[F-00](../../features/version2.0/F-00-모드체계와-범위경계.md) 5.3 의 모델 목록에 없다.
그런데 **계좌 초기화**(연습 계좌를 얼마로 되돌릴 것인가)와 **수익률 계산 기준선**
양쪽에 필요하다. 대회 계좌는 `Contest.initial_capital` 을 복사해 넣는다.

### B-3. `Contest.slug` · `portfolio_visibility`

- **`slug`**: 화면 URL 이 `/contests/<id>/` 로 적혀 있으나, 대회는 외부 공유가 잦아
  `/contests/rfm-1/` 형태가 낫다. `id` 노출도 피한다
- **`portfolio_visibility`**: [F-05](../../features/version2.0/F-05-랭킹-정산-스냅샷.md) 3.3 에
  **`Contest.portfolio_visibility`** 로 이미 등장하는데 [F-02](../../features/version2.0/F-02-대회-도메인.md) 5장
  모델 목록에는 빠져 있다. 목록 쪽 누락이다

### B-4. `Execution.is_assumed_depth` ★

[F-03](../../features/version2.0/F-03-주문-체결엔진.md) 5.1 4단계 —
지정가가 상대 10호가를 넘으면 **"평균 잔량이 1틱 간격으로 형성되어 있다고 가정"**하고 체결한다.
명세 스스로 *"실제 시장 상황보다 유리한 가정임을 화면에 명시"*하라고 적었다.

**화면에 명시하려면 데이터에 표시가 있어야 한다.** 조각별 불리언을 둔다.
v2.0 관통 원칙 ②("화면에 보이지 않는 사실은 없는 것과 같다")의 적용이다.

### B-5. `WeeklyTurnover.is_confirmed`

[F-04](../../features/version2.0/F-04-대회-규칙엔진.md) 5.2 가 **"확정 위반"과 "예상 위반"**을
나눠 보여주라고 했으나, 모델 목록에는 구분 필드가 없다. 플래그를 둔다.

### B-6. `ContestResult.port_hhi` · `pnl_hhi`

[F-04](../../features/version2.0/F-04-대회-규칙엔진.md) 6.2 가 관리 점수 산식을
**"v2.0 의 제안이며 확정이 아니다"**라고 명시했고, 1회 대회 후 조정을 전제한다.

**최종 점수만 저장하면 산식을 바꿨을 때 과거 대회를 재계산해 비교할 수 없다.**
중간 값(허핀달 지수 2종)을 함께 남긴다.

### B-7. `ContestSectorWeight.limit_pct`

섹터 한도 `max(시장비중 × 2, 10%)` 를 **미리 계산해 저장**한다.
주문마다 `rule_set` JSON 을 파싱해 재계산하면 그 비용이 주문 경로에 들어오고,
규칙을 바꿨을 때 과거 판정과 어긋난다.

### B-8. `QuoteCache.is_simulated` · `StockMaster.is_featured`

- **`is_simulated`**: [F-16](../../features/version2.0/F-16-시장데이터-파이프라인.md) 4.1 이
  "시뮬레이션 가격으로는 대회 주문을 절대 체결하지 않는다"를 요구한다.
  **체결 직전에 판정하려면 캐시 행에 표시가 있어야 한다**
- **`is_featured`**: [F-06](../../features/version2.0/F-06-주식-연습모드.md) 3장의
  **수업용 14종** 개념을 살리는 플래그. 시뮬레이션 폴백 대상이기도 하다

## C. 새로 발견한 v1.0 결함 (1건)

### C-1. `member` · `upbit_market` 만 `CHARSET=utf8` 이다

```sql
`member`       ... DEFAULT CHARSET=utf8    COLLATE=utf8_general_ci      -- 3바이트
`stock_order`  ... DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci   -- 4바이트
```

| 영향 | |
|---|---|
| **이모지가 든 사용자명을 저장할 수 없다** | MySQL 의 `utf8` 은 3바이트라 이모지가 안 들어간다 |
| 콜레이션이 다른 컬럼 간 조인 | MySQL 에서 인덱스를 못 타는 경우가 있다 |

**인벤토리 4장의 결함 11건에 없던 항목**이라 여기 기록한다.
**Postgres 로 가면 통째로 사라진다** — 문자셋이 데이터베이스 단위 하나뿐이다.
따로 조치할 것은 없고, "v1.0 을 계속 쓴다면 고쳐야 할 것"으로만 남긴다.

→ [03-v1.0-스키마-대조표](03-v1.0-스키마-대조표.md) 1.1

## D. 구현 방식만 조정한 것 (참고)

데이터 모델은 그대로이고 **접근 방법만** 바꾼 것이다. 명세 수정은 필요 없다.

### D-1. `ApiCallBudget` 은 잠금이 아니라 upsert 로 센다

[F-16](../../features/version2.0/F-16-시장데이터-파이프라인.md) 2.4 는
`SELECT ... FOR UPDATE` 로 적혀 있다. **카운터 증가에는 upsert 가 낫다.**

잠금은 트랜잭션이 끝날 때까지 다른 요청을 세우는데, **초당 5건짜리 창에서는
그 대기 자체가 유량을 낭비한다.** `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` 은
대기 없이 즉시 결과를 준다.

**캐시 행 갱신에는 여전히 `FOR UPDATE SKIP LOCKED` 를 쓴다** — 거긴 "한 명만 갱신하고
나머지는 결과를 기다린다"가 맞는 동작이다.

### D-2. 종목을 FK 로 걸지 않는다

`Order.symbol` · `Position.symbol` 은 문자열이고 `StockMaster` FK 가 아니다.
자산군이 섞이고(주식·코인·대체자산), 상장폐지가 이력을 막으며, 배치 갱신이 제약에 걸린다.

### E-1. 브로커 다중화 — `ExternalToken` 확장 ★

강사님 원본이 KIS 하나에서 **KB증권·Alpaca** 까지 넓어졌다
(upstream `cde723a` · `179b946` · `8798d1b`). [E-04](E-04-market.md) 8장은 KIS 단독을
전제해 `UNIQUE(provider)` 로 잡혀 있었다.

| | 변경 |
|---|---|
| `core.constants.BrokerProvider` | **신설** — `KIS` / `KB` / `ALPACA` / `UPBIT` |
| `core.constants.QuoteSource` | 시세 출처에 `KB` · `ALPACA` 추가 |
| `ExternalToken.provider` | 자유 varchar → `BrokerProvider` choices |
| **`ExternalToken.environment`** | **신설** — `MOCK` / `REAL` |
| 유니크 키 | `UNIQUE(provider)` → **`UNIQUE(provider, environment)`** |

**`environment` 가 필요한 이유** — KIS 는 모의/실전, Alpaca 는 Paper/Live 로
**같은 브로커에 자격증명이 둘**이다. `provider` 단독 유니크면 둘 중 하나만 캐시할 수 있다.

**1차 범위는 KIS 만 실사용이다.** KB 는 포털 승인 전이라 시세 경로가 없고
(원본 `broker_test.py` 주석이 그 상태를 정확히 적어 두었다), Alpaca 는 읽기 전용
계정 조회까지다. **모델 자리만 만들어 두고 폴백 체인에는 넣지 않는다.**

발급 절차는 **[api_발급_가이드](../../api/version2.0/api_발급_가이드.md)** 로 분리했다.
같은 문서에 **AWS 는 이 프로젝트에서 사용하지 않는다**(강사님 `e97d82f` 의 Lambda 연동
배제)를 명시했다.

### E-3. 인덱스 이름은 30자를 넘을 수 없다

### E-14. 권한 그룹 시드는 `Permission` 이 없는 상태에서 돈다 ★★

**Django 는 `Permission` 을 마이그레이션으로 만들지 않는다.** `contenttypes` 앱이
**`post_migrate` 시그널**에서 만드는데, 그건 **모든 마이그레이션이 끝난 뒤**다.

```
migrate ─┬─ 0001_initial ...
         ├─ 0004_seed_permission_groups   ← Permission 을 찾으면 0건
         └─ (전부 끝) → post_migrate → create_permissions()
```

빈 DB 에 `migrate` 하면 **그룹은 생기지만 권한이 하나도 안 붙는다.**
게다가 조용히 성공해서, 운영자가 Admin 에 들어가 아무것도 못 보고 나서야 발견된다.

**조치** — 시드 마이그레이션이 `create_permissions()` 를 **직접 먼저 호출**한다.
멱등이라 두 번 불려도 안전하다. 찾지 못한 권한이 하나라도 있으면 `RuntimeError` 로
**즉시 실패**시켜, 모델명 오타가 배포 후에 발견되는 일을 막는다.

부여 결과: `contest_admin` **23권한** · `content_admin` **10권한**.
**`delete` 는 아무에게도 주지 않았다** — 실격은 삭제가 아니라 `is_ranked=False` 이고,
레슨 삭제는 `LearningProgress` 의 `PROTECT` 가 막는다.

### E-18. `filter().bulk_create()` 는 **MANUAL 행을 지키지 못한다** ★★

| | |
|---|---|
| **명세** | [E-04](E-04-market.md) 4장의 예시 코드 |
| **실제** | `filter()` 가 `bulk_create()` 에 아무 영향을 주지 않는다 |
| **조정** | `ON CONFLICT … DO UPDATE … WHERE` 로 raw SQL 작성 |

```python
# E-04 4장에 적힌 코드 — 보호되지 않는다
TradingCalendar.objects.filter(source=CalendarSource.PYKRX).bulk_create(
    rows, update_conflicts=True, unique_fields=["date"], update_fields=["is_open"],
)
```

`bulk_create()` 는 `INSERT … ON CONFLICT` 문을 만들 뿐이라 **앞에 붙은 `filter()` 가
SQL 에 반영되지 않는다.** 조용히 성공하면서 운영자가 "임시 휴장"으로 고쳐 둔 날을
다음 배치가 되살린다. **임시 휴장일에 대회 정산이 도는 사고**로 이어진다.

Postgres 는 `ON CONFLICT DO UPDATE` 에 `WHERE` 를 붙일 수 있다. Django ORM 이
이것을 표현하지 못하므로 이 upsert 만 raw SQL 로 적었다::

    INSERT INTO trading_calendar (date, is_open, note, source) VALUES …
    ON CONFLICT (date) DO UPDATE SET is_open = EXCLUDED.is_open
     WHERE trading_calendar.source = 'PYKRX'
    RETURNING (xmax = 0) AS inserted

`RETURNING (xmax = 0)` 은 "이 행이 INSERT 였는가"를 알려주는 관용구다.
**`WHERE` 에 걸려 건너뛴 행은 아예 반환되지 않아** 그 차이가 곧 `skipped` 가 된다.

실검증: 2026-08-12 를 `MANUAL` · 휴장으로 바꾼 뒤 배치를 다시 돌려
`신규 0 · 갱신 224 · 건너뜀 1` 과 값 보존을 확인했다.

→ [E-04](E-04-market.md) 4장 예시 코드를 위 SQL 로 교체.

### E-19. `ApiCallBudget` 은 `now()` 가 아니라 **`clock_timestamp()`** 로 센다 ★★

| | |
|---|---|
| **명세** | [F-16](../../features/version2.0/F-16-시장데이터-파이프라인.md) 2.4 · [E-04](E-04-market.md) 6장 SQL 이 `date_trunc('second', now())` |
| **문제** | Postgres 의 `now()` 는 **트랜잭션 시작 시각**이다 |
| **조정** | `date_trunc('second', clock_timestamp())` |

`atomic()` 블록 안에서 예산을 차감하면 아무리 시간이 흘러도 `now()` 가 고정이라
수백 건이 **같은 1초 창에 몰린다.** 카운터가 즉시 한도를 넘고, 실제 호출 속도와
무관하게 배치가 스스로를 막아버린다. `clock_timestamp()` 는 문장이 실행되는 실제
벽시계를 준다.

**함께 지킬 규칙 — 예산 차감은 트랜잭션 밖에서 한다.** 트랜잭션이 롤백되면 카운터도
되돌아가는데 **호출은 이미 나갔다.** 되돌아간 예산은 거짓이다.

변경노트 D-1(잠금 대신 upsert)의 연장선이다. D-1 이 고른 upsert 방식은
**차감하고 나서 한도를 본다**는 뜻이라, 거절된 시도도 카운터에 남는다.
실측에서 한도 2인 KRX 창에 `3` 이 찍힌 것이 그 동작이다 — 실제 호출은 2건이고
3번째는 대기했다. `count` 는 "호출 수"가 아니라 **"시도 수"** 로 읽어야 한다.

→ [E-04](E-04-market.md) 6장 · [F-16](../../features/version2.0/F-16-시장데이터-파이프라인.md) 2.4 의 SQL 수정 + `count` 의 의미 한 줄 추가.

### E-23. `job_run` 은 **외부 조회까지** 감싸야 한다 ★★

처음에는 `job_run` 이 DB 쓰기만 감쌌다. "외부 호출은 트랜잭션 밖" 원칙을 지키려던
것인데, **원칙을 잘못 적용했다.**

    자격증명 누락 · 네트워크 장애 · 모델 다운로드 실패
      → job_run 밖에서 터짐 → DataSyncLog 에 아무것도 안 남음
      → pg_cron 이 불렀을 때 Admin 에 흔적이 없음
      → 운영자는 데이터가 왜 낡았는지 알 방법이 없음

**[E-07](E-07-core.md) 2.2 가 없애려던 "조용히 실패하는 배치" 그 자체다.**

`job_run` 은 **트랜잭션을 열지 않는다.** 행 2개를 쓸 뿐이라 느린 외부 호출을 감싸도
커넥션을 붙잡지 않는다. "외부 호출은 `atomic()` 밖"과 충돌하지 않는다.
네 서비스 모두 `job_run` 이 본체 전체를 감싸도록 고쳤다.

실검증: 자격증명을 비우고 실행 → `DataSyncLog [FAILED]` + 스택트레이스에 사유 기록 →
3회 반복 후 다음 실행에서 연속 실패 경고 표시까지 확인.

**dry-run 은 반대로 기록하지 않는다.** 연습 실행이 이력에 섞이면
`has_consecutive_failures()` 판정과 "마지막 성공 시각"이 거짓이 된다.

### E-24. 임베딩은 **모델 이름뿐 아니라 라이브러리 버전에도 묶인다**

### E-26. 적대적 코드 리뷰에서 잡은 **조용한 데이터 손상 2건** ★★

> 커맨드 4종이 실데이터로 다 돌아간 **뒤에** 돌린 리뷰에서 나왔다.
> 지적 28건 중 14건이 적대적 검증을 통과했고, 아래 둘은 **동작하는 코드가
> 잘못된 데이터를 만드는** 종류라 따로 남긴다. 실행이 성공하고 로그도 SUCCESS 인데
> 값만 틀리는 것들이라, 돌려보는 것만으로는 발견되지 않았다.

**① `avg_turnover_5d` 분모 불일치 — 대회 규칙이 헐거워진다**

`_recent_business_days()` 가 `TradingCalendar` 에서 최근 5건을 뽑을 때 **개수만 보고
`base_date` 까지 닿는지 확인하지 않았다.** 그런데 이 window 는 방향이 다른 두 곳에 쓰인다::

    분자  get_market_price_change(window[0], base_date)   ← base_date 까지 **누적**
    분모  len(window)                                     ← 5 로 **고정**

달력이 k영업일 뒤처지면 `avg_turnover_5d` 가 `(5+k)/5` 배로 부풀려진다.
이 값은 **"5일 평균 거래대금 30억 이하 매수 불가"** 의 분모다 — 부풀면
**막아야 할 저유동성 종목의 매수가 통과한다.**

**이 상태가 예외가 아니라 기본 운영 형태라는 것이 문제다.** `sync_trading_calendar` 는
연 단위 수동 실행이고 미래를 채울 수 없는데(E-20), `sync_stock_master` 는 매 영업일
16:00 에 도는 잡이다. 달력을 마지막으로 돌린 다음 영업일부터 바로 어긋나기 시작한다.

**조치** — 개수가 아니라 **범위**를 확인한다. 달력에 `base_date` 행이 있을 때만
달력을 쓰고, 없으면 pykrx 폴백으로 넘긴다(폴백은 `day <= base_date` 로 모으므로 정확하다).

**② 빈 응답이 전 종목을 상장폐지로 뒤집는다**

    if mark_delisted:
        StockMaster.objects.exclude(symbol__in=incoming).filter(is_delisted=False)\
                           .update(is_delisted=True)

`incoming` 이 빈 집합이면 **Django 가 `exclude(symbol__in=set())` 를 "조건 없음"으로
최적화해 전 행이 매칭된다.** 같은 트랜잭션의 `bulk_create([])` 는 되살려 주지 않는다.

**빈 응답이 예외 없이 도달할 수 있다는 것이 핵심이다.** pykrx 의
`dataframe_empty_handler`(`website/comm/util.py`)가 `KeyError`·`ValueError`·
`JSONDecodeError` 를 삼키고 **빈 DataFrame 을 반환**한다. 그래서 `retry` 도
`job_run` 의 FAILED 기록도 발동하지 않는다. 잡은 **"완료: 신규 0건" 과 함께 SUCCESS 로
기록**되고, 다음 날까지 대회·연습 모드의 종목 검색과 주문이 전부 막힌다.

**조치** — 상장종목 목록이 비면 쓰기 전에 `ExternalDataError` 로 중단한다.
업비트 경로에는 같은 가드가 이미 있었는데(`_fetch_upbit_markets` 의 빈 리스트 검사)
**훨씬 파괴적인 이쪽에만 없었다.**

**함께 고친 것 (같은 리뷰에서 확인된 것들)**

| # | 내용 |
|---|---|
| 상장폐지 판정 기준 | `incoming`(이름을 못 받아 제외된 종목이 빠진 부분집합) → **`universe`**(거래소 상장목록). 이름만 못 받은 정상 종목이 상장폐지로 뒤집히지 않게 |
| `--with-sectors` 업종 유실 | 업종을 못 받은 종목의 `sector_name` 이 빈 문자열로 덮이던 것을 두 묶음 upsert 로 분리 |
| 실패 시 `rows_affected=0` | `job_run` 이 성공·실패 모두 기록하도록. 달력은 월 단위 커밋이라 **실패해도 앞 달은 남아 있다** |
| 연초 당월 빈 데이터 | 진행 중인 달에 영업일이 없으면 그 달만 건너뛴다. 지나간 달의 실패는 그대로 올린다 |
| dry-run 숫자 불일치 | dry-run 이 MANUAL 보호를 반영하지 않아 실제 실행과 다른 수치를 보고하던 것. **dry-run 의 값어치는 실제와 같은 숫자를 내는 데 있다** |
| `--batch-size 0` · `--limit 0` | 220MB 모델을 다 받은 뒤 터지거나 0건 처리 후 SUCCESS 로 남던 것을 인자 검증으로 선차단 |

**교훈** — ①·② 둘 다 **"돌려봤더니 잘 되더라"로는 안 잡히는** 종류다.
①은 달력을 방금 동기화한 상태에서만 값이 맞고, ②는 외부가 정상일 때만 안 터진다.
**정상 경로가 통과하는 것과 코드가 옳은 것은 다르다.**

### E-27. **"검색 쿼리 임베딩은 동기" 는 다시 봐야 한다** ★

### E-29. `cron.job_run_details` 로는 **잡의 성패를 알 수 없다** ★★

`net.http_post()` 는 **요청 id 를 즉시 돌려주는 비동기 함수**다. 실제 HTTP 는
pg_net 워커가 나중에 보낸다. 그래서 이렇게 된다:

    앱이 꺼져 있어도            → cron.job_run_details.status = 'succeeded'
    토큰이 틀려 404 를 받아도   → succeeded
    잡이 예외로 죽어도          → succeeded

pg_cron 이 아는 것은 **"SQL 이 돌았다"** 까지다. F-20 5장이 `cron.job_run_details`
를 "pg_cron 자체 이력"이라고만 적어 둔 것을 그대로 읽으면, 운영자는 저 화면이
초록색인데 데이터가 안 들어오는 상황을 **원인 없이** 마주하게 된다.

관측 경로를 셋으로 나눠 문서·화면에 명시했다:

| 보는 곳 | 답하는 질문 |
|---|---|
| `cron.job_run_details` | SQL 이 제 시각에 돌았는가 |
| `net._http_response` | 응답이 몇 번으로 왔는가 (404·400·503·timeout 이 **여기** 보인다) |
| **`DataSyncLog`** | **잡이 무엇을 했는가 — 진실은 여기다** |

Admin 배너가 ①과 ③을 나란히 놓고, "여기가 성공이어도 잡이 성공한 것은 아니다" 를
화면에 적는다. → [F-20](../../features/version2.0/F-20-스케줄러.md) 5장에 이 표를 반영할 것.

### E-30. `on_progress` · `notes` 는 **응답 본문에 실어야 남는다**

세션 7 리뷰의 지적("지금은 pg_cron 경로에서 품질 정보가 사라진다")을 처리한 결과다.

그런데 이 잡들이 실제로 알려주는 것은 숫자가 아니라 품질 정보다:

    "2026년은 진행 중입니다 — 8월까지만"  ← 남은 넉 달은 아직 못 채웠다
    "배치가 건드리지 않는 필드: ..."      ← 이 값들은 배치를 믿으면 안 된다

★ 다만 pg_net 의 응답 보관은 몇 시간짜리다. **영구 기록은 여전히 `DataSyncLog`** 이고,

### E-33. 404 로 숨기되 **사유는 반대편에 적는다**

F-20 3.1 은 "토큰 불일치 시 404" 를 요구한다(403 은 경로 존재를 드러낸다).
그대로 만들면 규약 8.5("환경 가드는 막다른 길로 만들지 않는다")와 정면으로 부딪힌다 —
빈 404 는 **운영자에게도** 아무 단서가 없다.

답은 **사유를 응답이 아니라 서버 로그에 적는 것**이다.

    밖(응답):  404, 본문 없음
    안(로그):  "내부 엔드포인트 거부: POST /internal/jobs/x — X-Internal-Token 불일치 (from 10.0.0.5)"

그러려면 로깅 설정이 실제로 동작해야 한다. Django 기본값은 `django` 로거만,
그것도 `DEBUG=True` 일 때만 콘솔로 보낸다 — **우리 로거는 운영에서 그냥 사라진다.**
`settings.LOGGING` 을 명시해 루트에 콘솔 핸들러를 달았다. 이 설정이 없으면
위 설계가 성립하지 않는다.

★ DEBUG 화면도 막아야 한다. Django 의 기술 404 페이지는 **URL 패턴 목록을 통째로
보여준다.** `raise Http404` 대신 `HttpResponseNotFound()` 를 직접 반환한다.

### E-34. 자동 비활성화는 **HTTP 경로에만** 건다

F-20 5장의 "3회 연속 실패 시 잡을 자동 비활성화" 를 어디에 두느냐의 문제다.
CLI(`JobCommand`)는 이미 같은 상황에서 **경고만 하고 실행한다**(세션 7).

둘의 기대가 다르기 때문이다:

    스케줄러가 부른다 → 아무도 안 보고 있다 → 멈춰야 한다 (409 SKIPPED)
    사람이 손으로 돌린다 → 복구를 시도하는 중이다 → 실행해야 한다 (경고만)

같은 판정(`has_consecutive_failures`)을 쓰되 **반응을 다르게** 했다.
HTTP 쪽은 `{"force": true}` 로 넘어설 수 있게 두었다 — Admin 재실행 버튼이 쓸 통로다.
`dry_run` 도 막지 않는다. DB 를 건드리지 않는 것을 막을 이유가 없다.

### E-35. Django 조립 순서에서 걸린 것 2건 (Django 미경험자용 기록)

Admin 사이트를 갈아끼우면서 **연달아 두 번** 막혔다. 둘 다 "언제 import 되는가" 문제다.

**① `core/apps.py` 에 AppConfig 두 개를 두면 앱 등록이 깨진다.**

    RuntimeError: 'core.apps' declares more than one default AppConfig:
                  'AdminConfig', 'OpsAdminConfig'.

`INSTALLED_APPS` 의 `"core"` 를 풀 때 Django 가 `core.apps` 안의 AppConfig 후보를
훑는데, **import 해 온 `AdminConfig` 도 후보로 잡힌다**(`default = True` 라서).

**② 그렇다고 `core/admin_site.py` 로 옮기면 모델이 너무 일찍 로드된다.**
`INSTALLED_APPS` 항목은 **앱 레지스트리가 준비되기 전에** import 된다.
그 파일은 `job_health` → `core.models` 로 이어지므로 `AppRegistryNotReady` 가 난다.

→ `core/admin_apps.py` 를 따로 두고 **django.contrib.admin 외에는 아무것도
import 하지 않게** 했다. `default_site` 가 클래스가 아니라 **문자열**인 이유도
같다 — `admin.site` 에 처음 접근하는 시점(모델이 다 올라온 뒤)에 풀린다.

### E-39. `select_for_update` + nullable FK `select_related` 는 Postgres 가 거부한다 ★★

    NotSupportedError: FOR UPDATE cannot be applied to the nullable side of an outer join

`Account.contest` 는 nullable FK 다(연습 계좌는 비어 있다). `select_related("contest")`
가 **LEFT OUTER JOIN** 을 만들고, Postgres 는 그 outer join 의 nullable 쪽에 행 잠금을
걸 수 없다. 계좌를 잠그는 **모든 경로가 통째로 실패**했다 — 테스트 74건 중 44건.

```python
# 틀림 — 계좌 잠금이 필요한 곳마다 터진다
Account.objects.select_for_update().select_related("contest").get(pk=...)

# 맞음 — 계좌 행만 잠근다
Account.objects.select_for_update(of=("self",)).select_related("contest").get(pk=...)
```

**Django 미경험자가 밟기 쉬운 자리다.** SQLAlchemy 는 조인 전략을 손으로 고르는 일이
많아 이 조합이 잘 안 만들어졌는데, Django 는 `select_related` 가 조인을 자동으로 만들어
**더 쉽게 밟는다.** [E-03](E-03-trading.md) 9장의 예시 코드가
`Account.objects.select_for_update().get(pk=account_id)` 로 적혀 있어 그대로 쓰면
`select_related` 를 붙이는 순간 터진다 → **그 절에 `of=("self",)` 를 반영할 것.**

### E-41. 호가가 없으면 대회 주문이 **연습처럼 체결되고 있었다**

체결 방식을 고르는 분기가 처음에 이랬다.

```python
if is_contest and book is not None:
    return match_orderbook(...)      # 호가 소진
return match_at_price(quote.price, qty)   # 현재가 전량 즉시
```

호가 캐시가 비어 있으면 `book is None` 이 되어 **대회 주문이 두 번째 줄로 떨어진다.**
현재가에 전량 즉시 체결 — 그러면 연습 모드와 똑같아지고, **대회를 대회로 만드는
시장 충격이 통째로 사라진다.** 에러도 경고도 나지 않는다.

[F-16](../../features/version2.0/F-16-시장데이터-파이프라인.md) 3.4 가 "호가를 못 얻으면
주문을 거부하지 말고 `ACCEPTED` 로 남긴다"고 한 것이 바로 이 상황인데, 그 지시를
"거부하지 않는다"로만 읽으면 **체결해 버리는 쪽**으로 잘못 구현된다.

**대회는 호가 없이 체결하지 않는다**로 고치고 방어를 두 겹 뒀다(접수 경로와 매칭 경로).
→ F-16 3.4 에 "체결하지 않고 접수만 한다"를 명시할 것.

### E-42. 계좌 단위 트랜잭션에는 **주문마다 SAVEPOINT** 가 필요하다

잡 3 은 한 계좌의 미체결 주문들을 한 트랜잭션에서 처리한다(잠금 1회 · 처리 순서 결정적).
그런데 주문 하나가 `IntegrityError` 를 내면 **바깥 트랜잭션이 통째로 깨져**, 예외를
잡아도 이후 쿼리가 전부 `TransactionManagementError` 로 실패한다. 같은 계좌의 나머지
주문이 그 한 건에 끌려 죽는다.

```python
for order in account_orders:
    with transaction.atomic():        # ← 중첩 atomic 은 Django 에서 SAVEPOINT 다
        fill_open_order(order, quote, book)
```

FastAPI + SQLAlchemy 의 `session.begin_nested()` 자리와 같다. Django 는 `atomic()`
하나로 둘 다 표현한다 — **가장 바깥이면 트랜잭션, 안쪽이면 SAVEPOINT.**

### E-46. 실패 기록을 `atomic()` 안에서 하면 **예외와 함께 롤백된다** ★★

토큰 발급이 실패하면 그 사실을 DB 에 남겨 **다음 회차가 연타하지 않게** 해야 한다.
KIS 는 토큰 발급을 **1분에 1회**로 제한하고(`EGW00133`), 5초 잡이 회차마다
재발급을 시도하면 12번 두드려 전부 막힌다 — 복구가 오히려 늦어진다.

그런데 처음 구현은 기록이 **한 번도 남지 않았다.**

```python
with transaction.atomic():          # ← 토큰 행을 잠그는 구간
    ...
    payload = _issue_token(config)  # 실패 시 내부에서 _remember_failure() 호출
                                    # → 곧이어 던지는 예외가 그 기록까지 롤백한다
```

테스트가 잡았다 — "쿨다운 중에는 다시 두드리지 않는다" 가 `2 != 1` 로 깨졌다.
**증상이 조용한 결함이다.** 운영에서는 EGW00133 이 늘어날 뿐 아무도 원인을 모른다.

고친 모양은 "시도했는가" 만 밖으로 들고 나오는 것이다.

```python
attempted = False
try:
    with transaction.atomic():
        ...
        attempted = True
        payload = _issue_token(config)
except ExternalDataError:
    if attempted:            # 쿨다운으로 튕긴 것은 시도가 아니다 — 타이머를 되감으면 안 된다
        _remember_failure(config)
    raise
```

**같은 자리에서 두 번째 문제도 나왔다.** 행이 아직 없을 때는 `select_for_update()`
가 잠글 대상이 없어 두 프로세스가 **동시에 첫 발급**을 시도할 수 있다. 한쪽은 성공,
다른 쪽은 EGW00133 인데 — 실패한 쪽이 무조건 덮어쓰면 **방금 받은 멀쩡한 토큰이
지워진다.** `_remember_failure()` 가 유효한 토큰을 발견하면 그대로 두게 했다.

→ E-04 8장(`ExternalToken`)에 "발급 실패 표시는 `access_token=''`" 규약을 적을 것.

### E-47. 세션 9 의 테스트 9건은 **장중에만 통과했다** ★★

### E-49. "종목별 평균 비중" 이 **두 가지로 읽힌다** ★

F-04 6.2 는 관리 점수의 재료를 이렇게만 적었다:

> `종목별 평균 비중` 은 **일별 스냅샷의 평균**이다.

그대로 읽으면 계산이 둘 나오고 **결과가 다르다**:

```
① 일별 비중을 먼저 내고 평균     Σ_d (v_d / total_d) / 날짜수
② 평가액을 먼저 합치고 비중       Σ_d v_d / Σ_d total_d      ← 채택
```

①은 **보유가 하루도 없는 날을 어떻게 셀지**가 정해지지 않는다. 분모에서 빼면
"19일 현금 + 1일 몰빵" 이 몰빵 하루만으로 평가되고, 분모에 넣으면 현금으로 앉아
있을수록 비중이 희석돼 점수가 오른다. **어느 쪽이든 게임이 된다.**

②는 현금으로 있던 날이 분자·분모에 똑같이 0 을 더할 뿐이라 유리해지지도 불리해지지도
않고, 오래 크게 담은 종목일수록 비중이 커진다 — 원래 의도에 맞는다.

→ F-04 6.2 에 **식을 그대로 적어야 한다.** 문장만으로는 구현자마다 갈린다.

### E-50. HHI 를 **순자산 대비**로 재면 현금 100% 가 만점이다 ★★

"DB 에 아무것도 쓰지 않았습니다" 를 찍으면서 `WeeklyTurnover` 10행을 실제로 만들었다.

`compute_weekly_turnover()`(계산만)와 `refresh_weekly_turnover()`(저장)로 나눴다.
그러면서 dry-run 이 **더 유용해졌다** — 저장하지 않고도 "이대로 확정하면 누가 잘리는가"
를 읽기만으로 계산해 별칭까지 보여준다(`projected_violation_total`).

★ **교훈은 `--dry-run` 의 계약이 서비스 계층까지 내려가야 한다는 것이다.**
  `job_run(dry_run=True)` 이 `DataSyncLog` 를 남기지 않는 것만으로는 부족하다 —
  서비스 함수가 자기 판단으로 쓰면 그 약속이 깨진다.

### E-56. ★★ E-53 정정 — 10분 간격은 **월요일에 끝난 대회만** 지켜 준다

E-53 은 잡 9·10 의 순서 문제를 "대회가 **월요일에 끝날 때만** 드러난다" 로 적고,
잡 10 을 06:10 으로 옮겨 해결했다고 결론지었다. 또 *"코드로는 못 막고 스케줄로만
막힌다"* 고 단정했다. **둘 다 사실과 다르다. 실제로는 정반대다.**

```
잡 9  settle_weekly   UTC '0 21 * * 0'   → 주 1회, 일요일만 (= KST 월 06:00)
잡 10 settle_contest  UTC '10 21 * * *'  → 매일
```

10분 간격이 순서를 만드는 것은 **두 잡이 같은 날 도는 월요일뿐**이다. 나머지 6일은
앞에 아무것도 돌지 않는다 — 즉 **월요일 종료 대회가 유일하게 안전한 경우**이고,
화~일요일에 끝난 대회는 마지막 주가 미확정인 채 등급이 굳는다.

| | |
|---|---|
| **E-53 의 주장** | 월요일 종료만 위험하다 · 스케줄로 해결했다 |
| **실제** | 월요일 종료만 안전하다 · 나머지 6일은 무방비 |

실증했다. 금요일(2026-08-14) 종료 대회에서 마지막 주 4회째 위반자가 **1위(`final_rank=1`)**
를 받았다 (`contests.tests.SettleContestWeeklyGateTests`, 수정 전 코드에서 재현).
`apply_turnover_disqualification` 은 코드 전체에서 `settle_weekly` 안 **한 곳**에서만
불리고, `finalize_contest` 는 계좌를 얼리고 `CLOSED` 로 닫아 **앱 안에 되돌릴 길이 없다**
(`ContestAdmin.readonly_fields` 에 `status`, `ContestResultAdmin` 은 읽기 전용).

→ **코드로 막았다.** `_finalize_settling` 이 `finalize_contest` 를 부르기 전에
`_confirm_weeks_before_finalize()` 로 대회가 걸친 **미확정 주**를 스스로 확정하고
실격을 적용한다. 이미 확정된 주는 건드리지 않는다 — 확정의 주인은 `settle_weekly` 이고,
13주 × 100명이면 1,300 집계 쿼리가 확정 직전에 몰리기 때문이다.

→ F-05 4.3 에 *"최종 정산은 선행 주간 확정에 의존한다. 잡 10 은 그것을 기다리지 않고
   스스로 마감한다"* 를 명시할 것. F-20 표의 06:10 은 그대로 두되, **그 10분이
   안전장치가 아니라는 사실**을 각주로 남길 것.

### E-57. ★★ 비ASCII 토큰 헤더 하나로 **내부 경로가 드러났다** (운영 실측)

F-20 3.1 은 토큰 불일치를 403 이 아니라 **404** 로 주기로 했다. 경로의 존재를
숨기기 위해서다. 그런데 운영(`stock-coin-trade.vercel.app`)에 요청을 넣어 재어 보니:

```
X-Internal-Token: plainwrong    → 404   (의도대로)
X-Internal-Token: 한글토큰값     → 500 ★ (경로가 실재한다는 신호)
```

`hmac.compare_digest` 는 str 을 받으면 **양쪽이 ASCII 여야** 하고, 아니면 비교에
실패하는 게 아니라 `TypeError` 를 던진다. 헤더는 바깥에서 오는 값이라 무엇이든 들어온다.
예외가 미들웨어를 뚫고 나가 500 이 되고, **틀린 토큰 하나로 404 와 500 이 갈리므로
404 로 숨긴 설계가 통째로 무너진다.**

→ 바이트로 비교한다(`encode("utf-8", "surrogateescape")`). 기대 토큰은
   `token_urlsafe` 라 항상 ASCII 이므로 비ASCII 입력은 **조용히 불일치**로 떨어진다.
→ 판정 자체가 터져도 404 로 닫히도록 한 겹 더 감쌌다 (fail closed).
→ F-20 3.1 에 *"토큰 비교는 바이트로 한다"* 를 한 줄 넣을 것.

### E-58. 거부 404 의 **본문 길이**가 경로의 존재를 알려줬다

같은 실측에서 나온 두 번째 구멍이다. 상태코드는 같아도 본문이 달랐다:

```
/internal/jobs/     404 ·   0 B   ← 미들웨어의 빈 HttpResponseNotFound()
/없는-경로/          404 · 179 B   ← Django 기본 404
```

길이 0 인 404 만 골라내면 `/internal/` 아래가 실재한다는 사실을 확인할 수 있다.
**403 대신 404 를 쓴 이유가 무의미해진다.**

→ 운영에서는 `page_not_found()` 로 **Django 가 만들었을 바로 그 404** 를 돌려준다.
   `DEBUG=True` 일 때만 빈 본문을 유지한다 — 그때 `page_not_found` 는 URL 패턴
   목록을 통째로 보여주는 기술 404 페이지를 내기 때문이다.
→ ★ `templates/404.html` 을 나중에 만들 때 `base.html` 을 확장하면, 그 안의
   네비게이션 조회가 **거부된 요청마다** 돈다. 토큰 없이 두드리는 것만으로 DB 부하가 된다.

### E-59. pykrx 3종은 **Vercel 에서 구조적으로 못 돈다** — 로컬 CLI 로 뺀다

`requirements.txt` 가 **두 개**이고 서로 다르다:

```
루트 requirements.txt       Django · requests · …  (pykrx 없음)   ← Vercel 이 설치하는 것
backend/requirements.txt    pykrx==1.2.8                          ← 로컬 전용
```

`vercel.json` 의 `@vercel/python` 빌더는 **루트**를 본다. 따라서 `sync_stock_master` ·
`sync_trading_calendar` · `sync_market_index` 를 pg_cron 에 등록하면
`ModuleNotFoundError` 로 즉사한다. 설사 번들에 넣어도 KRX 로그인 자격증명
(`KRX_ID`·`KRX_PW`)이 없고(VERCEL.md 3.2), `sync_stock_master` 는 실측 88초다.

**세 겹의 벽이라 등록해도 데이터가 한 줄도 안 채워진다.** 그런데도 등록하면 매 영업일
실패가 쌓여 Admin 배너가 상시 빨개지고, 정작 봐야 할 실패가 묻힌다
(`job_health.py` 의 "평소에 아무것도 안 보여야 빨간 배너가 눈에 띈다" 원칙).

→ 셋 다 **로컬 CLI**로 돌린다. 코드는 그대로다 — CLI 와 HTTP 가 같은 서비스 함수를
   부르므로(F-16 5.3) 상시 기동 서버가 생기면 SQL 주석만 풀면 된다.
→ ★ 연말 주의 — `sync_trading_calendar` 는 인자를 생략하면 **부르는 시점의 연도**만
   채운다. 1월에 돌리면 전년 12월이 영영 빈다. 연초에 `--year <전년도>` 를 한 번 더.

### E-60. ★★ Vercel 배포 URL 이 **두 종류**이고, 하나는 pg_net 이 못 쓴다

`vercel ls` 가 알려주는 주소를 그대로 Vault 에 넣으면 잡이 **전부 조용히 실패**한다.

```
stock-coin-trade-<해시>-<팀>.vercel.app   → 302 vercel.com/sso-api   ✗ Django 에 도달 못 함
stock-coin-trade.vercel.app               → 200 / 404                ✓ 안정 별칭 (vercel alias ls)
```

Deployment Protection(SSO)이 배포 URL 에는 걸리고 프로덕션 별칭에는 안 걸린다.
문제는 **pg_cron 이 이것을 성공으로 기록한다**는 점이다 — `net.http_post` 가
request_id 를 돌려주기만 하면 `cron.job_run_details` 는 `succeeded` 다.
**잡 5개가 초록불을 켠 채 아무것도 안 하는 상태**가 며칠 갈 수 있었다.

→ SQL 에 **1.5장 배선 게이트**를 신설했다. `ops.ping_internal()` 로 부수효과 없는
   `GET /internal/jobs/` 를 쳐 **200 을 확인하기 전에는 잡을 등록하지 않는다.**
   302·404·400·308 각각의 원인과 조치를 범례로 붙였다.
→ `base_url` 은 함수 안에서 `rtrim(base_url, '/')` 로 끝 슬래시를 자른다. 하나 남으면
   `//internal/...` 이 되어 미들웨어의 `startswith('/internal/')` 를 빗나가고,
   **토큰 검사도 거부 로깅도 돌지 않아** 원인 없는 404 가 된다.

### E-61. ★★ **토막 주**를 위반으로 세는 규칙이 명세에 없다 — 결정 필요

F-04 5.1 은 주를 "월요일 00:00 ~ 일요일 24:00 KST" 로 정하고 회전율 5% 미만을
위반으로 센다. 그런데 **대회가 주 전체를 덮지 않는 경우의 규정이 없다.**

`compute_weekly_turnover` 의 분모는 **평균** 운용금액이다(합계가 아니다):

```
avg_asset = Σ total_asset / day_count      ← 스냅샷이 있는 날로만 나눈다
turnover_pct = (매수 + 매도) / avg_asset
```

분모가 평균이므로 **하루짜리 토막 주도 5일 주와 똑같은 절대 매매금액**을 요구한다.
대회 마지막 날 포지션을 정리만 하고 매매를 멈추는 것은 지극히 정상인데, 그 주는
자동으로 위반 1회가 된다. 첫 주도 같다 — 수요일에 시작한 대회의 첫 주는 3일뿐이다.

**이번 세션에 실측으로 드러났다.** 세션 12 의 `_confirm_weeks_before_finalize` 가
토막 막주까지 확정하자, 확정 위반 3회(허용 3회)로 통과하던 참가자가 4회째를 받아
**등급을 박탈당했다** — 대회가 끝난 뒤라 만회할 방법이 없다.

→ **당장은 토막 주를 확정 대상에서 뺐다.** 확정을 앞당기는 것이 그 함수의 일이지
   **판정 기준을 바꾸는 것은 아니기** 때문이다. 토막 주는 예전처럼 대회가 닫힌 뒤
   `settle_weekly` 가 확정하므로 등급에 영향이 없다 — 세션 11 이전과 같은 동작이다.

→ ★ **그러나 사각 자체는 남아 있다.** 대회 기간 중에 낀 토막 주가 없을 뿐,
   `settle_weekly` 는 여전히 첫 주·막주 토막을 위반으로 센다(화면·경고에 반영된다).
   F-04 5.1 에 다음 중 하나를 **명시해야** 한다:

   | 안 | 규칙 | 성질 |
   |---|---|---|
   | A | 대회가 온전히 덮지 않는 주는 위반으로 세지 않는다 | 단순 · 4주 대회에서 셀 수 있는 주가 2주로 줄 수 있다 |
   | B | 덮인 **영업일이 3일 미만**이면 세지 않는다 | 실질적 · 기준선을 하나 더 정해야 한다 |
   | C | 분모를 덮인 일수에 비례해 줄인다 | 가장 공평 · 계산이 바뀐다 |

   **B 를 권한다.** A 는 4주 대회에서 실격이 사실상 불가능해지고, C 는 회전율의
   정의를 바꿔 이미 쌓인 데이터와 어긋난다.

### E-62. 최종 정산은 **모수가 완전할 때만** 굳힌다

`_confirm_weeks_before_finalize` 가 참가자 한 명에서 예외를 만나면, 예전 초안은
note 만 남기고 `finalize_contest` 를 그대로 불렀다. 검토에서 실측으로 드러났다 —
회전율 0% 로 4주를 보낸 참가자가 확정 실패 하나로 **1위·B등급**을 받았다.

백분위는 **모수가 맞아야** 뜻이 있다. 실격됐어야 할 사람이 랭킹에 남으면 그 사람만
틀리는 게 아니라 **아래 참가자 전원의 등급이 함께 이동한다.** 그런데 `CLOSED` 는
`ClosedContestGuardMixin` 이 참가 편집을 막고 `ContestResultAdmin` 이 읽기 전용이라
앱 안에 되돌릴 길이 없다.

→ 확정 실패가 하나라도 있으면 **그 대회는 오늘 닫지 않는다.** `SETTLING` 으로 남고
   `_finalize_settling` 이 매일 그 상태를 다시 긁으므로 내일 자동 재시도된다.
   **되돌릴 수 없는 것과 하루 늦는 것 사이에서는 후자가 항상 싸다.**

→ ★ `DataSyncLog` 에는 notes 필드가 없어 이 실행이 **SUCCESS 로 기록된다.**
   연기 사실은 HTTP 응답 body 에만 실린다. F-19 Admin 배너에 "확정이 미뤄진 대회"
   를 띄우거나, `DataSyncLog` 에 note 를 남길 자리를 만드는 것이 다음 과제다.

**E-29 는 F-20 5장을 읽는 방식 자체를 바꾼다.** `cron.job_run_details` 를
"pg_cron 자체 이력"으로만 적어둔 지금 문장을 그대로 믿으면, 운영자는 초록색
화면 앞에서 데이터가 왜 없는지 영원히 알 수 없다. 관측 경로 3단 표를 5장에 넣어야 한다.

**E-31 은 F-04 3.2 에 규칙 한 줄이 빠져 있다는 뜻이다.** 업종 미부여 종목의 취급을
적지 않으면 구현자마다 다르게 처리한다 — 그중 하나는 섹터 한도를 통째로 우회한다.

**E-36 은 E-28 의 선택지 하나가 애초에 유효하지 않았다는 정정이다** (2026-08-13 추가).
EC2 는 세션 1 에서 이미 폐기된 결정이고, **비용 0 이 최우선 제약**이다. 그 아래에서
잡 3 의 답은 "파이썬 한 벌 + 주기는 설정값 + 대회 기간엔 로컬 `--loop`" 다.
F-20 2장의 "5초" 를 "기본 5초, 설정값" 으로 고쳐야 한다.

**E-38 · E-39 는 문서의 코드 예시가 그대로는 위험하거나 동작하지 않는 것들이다.**
E-39 는 E-03 9장 예시에 `of=("self",)` 를 더해야 하고, E-38 은 F-03 5.1 4단계에
"평균 잔량은 자산군 단위로 절사한다" 를 한 줄 넣어야 한다. 안 적으면 다음 구현자도
같은 자리에서 소수 주를 만든다.

**E-40 은 시드가 명세와 다른 값을 넣고 있었다는 뜻이다.** 세션 6 시드를 검증 없이
믿으면 연습 모드 수수료가 7배가 된다. `core/0003` 이 고쳤다.

**E-43 은 착수 전제라 먼저 알린다** (2026-08-13 세션 10 추가). F-16 2.4 의 "초당 5건 =
분당 300건" 이 **우선순위 폴링 설계 전체의 바탕**인데, 그 5가 자료마다 다르다.
실제가 초당 1건이면 분당 60건이고 2.5 의 주기표(미체결 5초 · 보유 30초)를 다시 짜야
한다. **KIS 키가 생기면 가장 먼저 실측할 항목이다.** 코드는 그때까지 보수적인
기본값으로 돌고, `.env` 의 `KIS_RATE_LIMIT` 으로 조절할 수 있다.

**E-50 은 그냥 두면 관리 점수가 정반대로 작동한다** (2026-08-14 세션 11 추가).
F-04 6.2 의 "비중" 을 다른 절과 같은 뜻(순자산 대비)으로 읽으면 **전액 현금인 참가자가
포트 분산 만점**을 받는다. 몰빵을 막으려는 지표가 아무것도 안 한 사람을 1등으로 올린다.
분모를 명시하는 한 줄이면 막을 수 있다.

**E-53 은 대회가 월요일에 끝날 때만 드러난다.** 잡 9·10 이 F-20 표에서 둘 다 06:00 이라
같은 분에 걸리는데, pg_cron 은 순서를 보장하지 않는다. 실격 확정보다 최종 정산이 먼저
돌면 **실격자가 등급을 받는다.** 코드로는 못 막고 **스케줄로만** 막힌다 — 그래서
잡 10 을 06:10 으로 옮겼고, 표를 고치지 않으면 다음 사람이 06:00 으로 되돌린다.

**E-47 은 앞선 세션의 보고를 정정한다.** 세션 9 의 "테스트 150건 통과" 는 사실
**"장중에 돌리면 150건 통과"** 였다. 지금은 시각을 고정해 언제 돌려도 같은 답이 난다.
다음 세션이 장외에 시작해 실패를 자기 탓으로 오해하는 일을 막는다.
