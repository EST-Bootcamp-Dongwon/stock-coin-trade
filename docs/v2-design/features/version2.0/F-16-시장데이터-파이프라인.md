## 2. 캐시 아키텍처 ★

### 2.1 원칙

> **모든 캐시는 Supabase Postgres 테이블에 있다.
> 요청을 넘어서 사는 프로세스 메모리 캐시는 만들지 않는다.**

v1.0 결함 D-9 의 재발 방지선이다. v1.0 은 시세·차트·뉴스·랭킹 캐시와
Open API rate limit 이 전부 전역 `dict` 였고, 서버리스로 가면 전부 무력화된다.

### 2.2 허용되는 유일한 메모리 캐시

**요청 단위 캐시**만 허용한다. 하나의 HTTP 요청 안에서 같은 종목을 여러 번
조회하면 두 번째부터 파이썬 딕셔너리에서 꺼내고, 요청이 끝나면 버린다.

```python
# Django 미들웨어 또는 요청 스코프 객체에 담는다
# 요청이 끝나면 GC 된다 — 다음 요청과 공유되지 않는다
```

### 2.3 캐시 테이블

| 테이블 | 키 | TTL | 비고 |
|---|---|---|---|
| `QuoteCache` | symbol | 10초(장중) / 무제한(장외) | 현재가·등락률·거래량 |
| `OrderbookCache` | symbol | 5초(장중) | 10단계 호가·잔량 (KIS) |
| `ChartCache` | symbol, interval | 300초 | 봉 데이터 |
| `IndexCache` | index_code | 60초 | KOSPI·KOSDAQ 지수 |
| `NewsCache` | source | 300초 | KRX 뉴스 |
| `ApiCallBudget` | api_name, window_start | — | **유량 관리** (2.4절) |

**TTL 은 컬럼(`expires_at`)으로 관리한다.** 조회 시 `expires_at > now()` 를 확인하고,
만료됐으면 갱신한다.

### 2.4 KIS 유량 관리 ★

KIS 모의투자 API 는 **초당 5건** 제한이다(실전 20건).
초과하면 `EGW00201` 유량 초과 오류가 난다.

**서버리스에서는 각 인스턴스가 자기가 몇 번 호출했는지만 알기 때문에,
전역 예산을 DB 에서 관리하지 않으면 반드시 터진다.**

```
호출 직전:
  BEGIN;
  SELECT count FROM api_call_budget
   WHERE api_name='KIS' AND window_start = date_trunc('second', now())
   FOR UPDATE;
  -- count >= 5 이면 → 대기하거나 캐시값으로 응답
  -- count < 5 이면 → count + 1 후 호출
  COMMIT;
```

**동시 갱신 방지**는 `SELECT ... FOR UPDATE SKIP LOCKED` 로 한다.
같은 종목을 여러 요청이 동시에 갱신하려 하면 **한 요청만 잡고 나머지는
그 결과를 기다렸다가 읽는다.**

### 2.5 우선순위 기반 폴링

초당 5건 = 분당 300건이다. 전 종목(2,700여 개)을 주기적으로 갱신하는 건 불가능하다.
**필요한 것만 갱신한다.**

| 우선순위 | 대상 | 주기 |
|---|---|---|
| 1 | 대회 참가자가 **미체결 주문을 걸어둔 종목** | 5초 |
| 2 | 대회 참가자가 **보유 중인 종목** | 30초 |
| 3 | 참가자가 **화면에서 보고 있는 종목** (관심종목·검색 결과) | 요청 시 on-demand |
| 4 | 그 외 | 요청 시 on-demand (캐시 만료 시에만) |

`SubscriptionRegistry(symbol, priority, last_polled_at)` 테이블로 관리하고,
pg_cron 잡이 우선순위 순으로 예산 안에서 갱신한다.

> **호가(`OrderbookCache`)는 대회 모드에서만 필요하다.**
> 연습 모드는 v1.0 방식(현재가 기준 즉시 체결 + 파생 호가 표시)이라 KIS 를 쓰지 않는다.
> 이게 유량 부담을 크게 줄인다.

## 3. ① 주식 호가 — KIS Developers

### 3.1 인증

| 항목 | 값 |
|---|---|
| 키 | `KIS_APP_KEY` / `KIS_APP_SECRET` — **서버 환경변수에만** 둔다 |
| 토큰 | `POST /oauth2/tokenP` → 24시간 유효 |
| 서버 | 모의투자 도메인 (`openapivts.koreainvestment.com`) |
| 거래 ID | 모의투자는 **`VTTC` 계열** |

> 학습가이드 (b) 한국투자증권 KIS Developers 문서가 **"키는 브라우저가 아닌 서버에만 둡니다"**를
> 첫 원칙으로 명시하고 있다. 이 문서의 내용을 실제로 실천하는 셈이다.
> → [F-17 학습 콘텐츠](F-17-학습콘텐츠.md)와 상호 참조를 걸어둔다.

**토큰은 `ExternalToken` 테이블에 저장한다.** 서버리스라 메모리에 두면
매 콜드스타트마다 재발급하게 되고, 발급 자체에도 유량 제한이 있다.

### 3.2 조회 항목

| 용도 | API |
|---|---|
| 호가 10단계 + 잔량 | 주식현재가 호가/예상체결 |
| 현재가 | 주식현재가 시세 |

### 3.3 장 시간 밖 처리

KIS 호가는 장중에만 의미가 있다. 장외에는:

- 대회 주문은 `PENDING_OPEN` 으로 접수만 하고 체결하지 않는다 (→ [F-03](F-03-주문-체결엔진.md) 8장)
- 화면에는 **마지막 장중 호가**를 "장 마감 시점 기준"이라고 명시해 보여준다

### 3.4 실패 시 폴백

KIS 가 죽으면 대회 체결이 멈춘다. 이건 심각하므로 명시적으로 처리한다.

```
KIS 호출 실패
  → 캐시된 마지막 호가가 5분 이내면 그것으로 체결 (경고 로그)
  → 5분 초과면 주문을 REJECTED 하지 않고 ACCEPTED 로 남긴다
    · 참가자에게 "시세 서버 지연으로 체결이 지연되고 있습니다" 표시
    · 복구되면 다음 폴링에서 체결
  → 운영자에게 알림 (Admin 대시보드 경고 배너)
```

**주문을 거부하지 않는 게 중요하다.** 우리 쪽 장애로 참가자가 기회를 잃으면 안 된다.

## 4. ② 주식 현재가·차트 — 3단 폴백 (v1.0 승계)

v1.0 의 3단 폴백은 **잘 만든 설계라 그대로 가져간다.**

```
1순위  yfinance          005930.KS 형태
2순위  네이버 금융        6자리 숫자 종목코드만
3순위  시뮬레이션         수업용 14종에 한해서만
```

### 4.1 v1.0 의 안전장치를 반드시 유지한다 ★

> v1.0: *KRX 에서 검색해 들어온 종목은 **가짜 가격으로 주문되지 않도록 503 을 던진다.***

이 판단은 정확했다. v2.0 에서도:

- **시뮬레이션 가격으로는 대회 주문을 절대 체결하지 않는다.**
- 연습 모드에서만 시뮬레이션 폴백을 허용하고, **화면에 "시뮬레이션 가격" 배지**를 단다.
- v1.0 은 이 사실이 코드에만 있고 화면에 없었다. v2.0 은 **사용자에게 보이게** 한다.

### 4.2 대회 모드는 KIS 를 1순위로

| 모드 | 시세 순위 |
|---|---|
| 대회 | KIS → 네이버 → (시뮬레이션 금지, 체결 보류) |
| 연습 | yfinance → 네이버 → 시뮬레이션(14종) |

## 5. ③ 종목 마스터 — pykrx 일배치 ★

대회 규칙 판정에 필요한 모든 속성을 **장 마감 후 1회** 수집해 `StockMaster` 에 적재한다.

### 5.1 수집 항목

| 항목 | pykrx 함수(개념) | 규칙 용도 |
|---|---|---|
| 종목 목록 · 시장 구분 | 상장종목 목록 | 유니버스 |
| 종목 유형 (보통주/우선주/ETF/ETN/리츠/스팩) | 종목 마스터 | 보통주만 허용 |
| 시가총액 | 시가총액 조회 | 시총 1000억 / 1조 판정 |
| 5일 거래대금 | OHLCV 거래대금 5일 | 30억 이하 매수 불가 |
| 상장일 | 상장 정보 | 신규·재상장 6영업일 |
| 관리종목 · 투자경고 단계 | 시장경보·관리종목 | 거래 차단 |
| **업종분류 (KRX)** | 업종 분류 | **GICS 대체** — 섹터 한도 |
| 영업일 | 영업일 조회 | `TradingCalendar` |

### 5.2 GICS 대체 명시 ★

타임폴리오는 GICS 산업군 기준으로 섹터를 나눈다. **GICS 는 MSCI·S&P 의 유료 데이터**라
사용할 수 없다.

- **KRX 업종분류를 쓴다.**
- 이 사실을 **대회 규칙 안내문과 섹터 화면에 명시**한다.
  ("본 대회의 섹터 구분은 KRX 업종분류를 따릅니다. GICS 와 다를 수 있습니다.")
- `ContestUniverse` 에 대회 시작 시점의 업종을 고정한다(→ [F-02](F-02-대회-도메인.md) 3.4).

### 5.3 실행 위치

pykrx 는 파이썬 라이브러리라 SQL(pg_cron) 에서 직접 못 돌린다.

```
pg_cron (매 영업일 16:00 KST)
   └─ pg_net 으로 HTTP 호출 ─▶ Django 관리 엔드포인트 /internal/jobs/sync-stock-master
                                 (내부 토큰 인증, 외부 노출 금지)
                                  └─ pykrx 수집 → StockMaster upsert
```

> **Django 관점** — FastAPI 였다면 `APScheduler` 나 별도 워커를 띄웠을 것이다.
> Django 에서는 `management/commands/` 에 커맨드를 만들어두면
> `python manage.py sync_stock_master` 로도 돌릴 수 있다.
> 같은 로직을 **HTTP 엔드포인트와 CLI 커맨드 양쪽에서 재사용**하도록
> 서비스 함수로 분리해 둔다. 로컬 개발·수동 재실행이 훨씬 편해진다.

## 6. ④ 코인 시세 — v1.0 승계

| 항목 | 처리 |
|---|---|
| 실시간 시세 | 업비트 WebSocket. **nginx 중계 유지** (`proxy_set_header Origin "";` 가 CORS 우회의 핵심) |
| 국내 4사 비교 | 업비트·빗썸·코인원·코빗 동시 조회. 개별 실패는 `null` 로 흘려보냄 (v1.0 `_fetch_price_safely` 승계) |
| 마켓 목록 | 업비트 `/v1/market/all` — 일 1회, **없는 것만 추가**(upsert) |
| 코인 랭킹 | **KRW 마켓 기준으로 재정의** (아래) |

### 6.1 코인 랭킹 재정의 ★ (결함 D-3 해소)

v1.0 은 CoinMarketCap Top 100(USD 기준)을 매시 `TRUNCATE` 후 재적재했는데
**어느 화면에서도 쓰지 않았다.** 거래는 KRW 기준이라 데이터가 연결되지도 않았다.

v2.0:

- **업비트 KRW 마켓의 24시간 거래대금 기준 랭킹**으로 바꾼다
- 소스는 업비트 자체 (CoinMarketCap 키 의존 제거)
- **코인 연습 화면에 실제로 붙인다**
- `TRUNCATE` → **upsert** 로 변경 (동기화 중 빈 테이블이 보이는 창 제거)

### 6.2 Vercel 서버리스와 WebSocket

**서버리스 함수는 WebSocket 상시 연결을 유지할 수 없다.**
v1.0 은 nginx 가 중계하고 **브라우저가 직접** 업비트 WebSocket 에 붙는 구조였다.
이 구조를 유지하면 서버리스에서도 문제가 없다.

- 브라우저 ↔ 업비트 WebSocket: **직접 연결** (중계 경로만 제공)
- 서버는 잔고 평가·주문 처리 때만 REST 로 시세를 확인

## 7. ⑤ KRX 뉴스 — v1.0 승계 + 캐시 이전

| 항목 | v1.0 | v2.0 |
|---|---|---|
| 캐시 | 프로세스 메모리 5분 | **`NewsCache` 테이블** |
| 수집 | 요청 시점에 외부 호출 | **pg_cron 이 주기 수집** → 요청은 DB만 읽음 |
| 실패 | 503 + 빈 배열 | **마지막 성공분을 제공** + 수집 실패를 로그·Admin 에 남김 |

> v1.0 은 비공식 엔드포인트 + PDF 경로 규칙 추측이라 언제든 깨질 수 있다.
> 깨졌을 때 **조용히 빈 화면이 되지 않도록** 관측 가능하게 만드는 게 v2.0 의 개선점이다.
