## D-7 상세 — 시드 데이터 정리

### 현재 상태

| | 실제 |
|---|---|
| README 서술 | `test1@test.com` · `test2@test.com` 이 앱 시작 시 자동 생성 |
| 코드 | **존재하지 않음.** `demo_seed.py` 의 `sample-investor-NN@sample-investor.local` 30개만 생성 |

### v2.0 처리

```
python manage.py seed_demo [--users N] [--contest]
```

| 옵션 | 생성물 |
|---|---|
| 기본 | 데모 계정 2개(`demo1` · `demo2`) + 연습 계좌 3개씩 |
| `--users N` | 샘플 투자자 N명 (기본 30 — v1.0 승계) |
| `--contest` | 진행 중 데모 대회 1개 + 참가자·주문·스냅샷 |

- **앱 시작 시 자동 생성하지 않는다.** 명시적으로 실행할 때만.
  (v1.0 은 `ensure_tables()` 처럼 기동 시 부수효과를 일으키는 패턴이 있었다)
- **README 를 코드에 맞춰 수정**한다. 반대가 아니다.
- 데모 계정은 `settings.DEBUG` 또는 환경변수가 켜져 있을 때만 생성 허용.
  **운영 환경에 데모 계정이 생기지 않게** 막는다.

| 환경 | 방식 |
|---|---|

## 처리 원칙 3가지

이번 정리에서 세운 원칙이다. 앞으로도 적용한다.

### 1. 죽은 코드를 남기지 않는다

D-1·D-2·D-3 은 전부 **"만들었는데 화면에 안 붙은 것"**이다.
v2.0 에서는 **기능을 만들면 반드시 진입점을 만든다.**
진입점을 만들 수 없으면 그 기능은 1차 범위에서 뺀다.

### 2. 화면에 보이지 않는 사실은 없는 것과 같다

D-11(이름-실제 불일치), 파생 호가, 시뮬레이션 가격 — 전부 **코드에만 있고
사용자에게는 안 보이던 사실**이다. v2.0 은 배지·주석으로 화면에 드러낸다.

### 3. 서버리스 전제를 처음부터 지킨다

D-8·D-9 는 **"프로세스가 계속 살아 있다"는 전제**에서 나온 결함이다.
v2.0 은 프로세스가 언제든 죽는다고 가정하고 설계한다.
**요청을 넘어서 사는 상태는 전부 DB 에 둔다.**
