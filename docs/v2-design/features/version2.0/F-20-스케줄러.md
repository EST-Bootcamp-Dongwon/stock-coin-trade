> **문서 버전** v2.0 · **작성일** 2026-08-11 (KST) · **분류** 기능=대체 · 구현=재작성

## 1. 왜 바꾸는가

| | v1.0 | v2.0 |
|---|---|---|
| 방식 | APScheduler `BackgroundScheduler` (Flask 프로세스 내 스레드) | **Supabase pg_cron** |
| 문제 | **서버리스에서 프로세스가 죽으면 함께 죽는다.** 워커가 여러 개면 잡이 중복 실행된다 | DB 안에서 돌아 프로세스와 무관 |
| 잡 수 | 2개 | 9개 |

Vercel Hobby cron 은 **하루 1회 · UTC · ±1시간 오차**라 "매 영업일 15:40 KST 정산"
같은 요구를 못 맞춘다. pg_cron 이 유일한 현실적 선택이다.

> **Django 관점** — FastAPI 에서는 `@app.on_event("startup")` 에 APScheduler 를 붙이는 게
> 흔한 패턴이다. Django 에서도 `AppConfig.ready()` 에 같은 짓을 할 수 있지만
> **하지 않는다.** 서버리스에서 무의미하고, `ready()` 는 `manage.py` 커맨드에서도
> 호출되어 마이그레이션 중에 잡이 뜨는 사고가 난다.

### 2.1 잡 3번이 핵심이다

`match_pending_orders` 가 [F-03](F-03-주문-체결엔진.md)의 절충안을 성립시키는 잡이다.
비동기 워커를 만들지 않는 대신, **이미 도는 시세 잡에 체결 추종을 얹는다.**

```
5초마다:
  ① 호가·현재가 갱신 (잡 2)
  ② 같은 트랜잭션에서 PARTIAL/ACCEPTED 주문 스캔
  ③ 시장 체결 조건 충족분 체결
  ④ STOP 발동 조건 확인 → 시장가 전환
```

**같은 트랜잭션**이라는 게 중요하다. 시세는 갱신됐는데 주문은 옛 가격으로
체결되는 창이 생기지 않는다.

## 3. 실행 방식

pg_cron 은 SQL 만 실행할 수 있다. 파이썬 로직(pykrx·KIS SDK)은 못 돌린다.
따라서 **두 갈래**로 나눈다.

| 유형 | 방식 | 해당 잡 |
|---|---|---|
| **순수 SQL** | pg_cron 이 직접 실행 | 7(정산 일부) · 9 · 10 · 14 |
| **파이썬 필요** | pg_cron → `pg_net` HTTP → Django 내부 엔드포인트 | 1 · 2 · 3 · 4 · 5 · 6 · 8 · 11 · 12 · 13 |

```sql
-- 개념 예시
SELECT cron.schedule(
  'sync_stock_master',
  '0 7 * * 1-5',                          -- UTC 07:00 = KST 16:00, 월~금
  $$ SELECT net.http_post(
       url     := 'https://<앱주소>/internal/jobs/sync-stock-master',
       headers := '{"X-Internal-Token": "..."}'::jsonb
     ); $$
);
```

### 3.1 내부 엔드포인트 보안

`/internal/jobs/*` 는 **외부에 절대 노출하면 안 된다.**

- `X-Internal-Token` 헤더 검증 (환경변수와 대조)
- Django 미들웨어에서 `/internal/` 접두사를 일괄 검사
- 토큰 불일치 시 **404** 반환 (403 을 주면 경로 존재가 드러난다)

> v1.0 결함 D-6 의 교훈 — AI·RAG 엔드포인트가 인증 없이 열려 있었다.
> v2.0 은 **내부 잡 엔드포인트를 처음부터 잠그고 시작한다.**

## 4. 초 단위 스케줄 — **실측 완료 · 지원됨** ✅

> **2026-08-13 개정 (세션 5 · 변경노트 E-2 반영)** — 착수 전 갈림길이었던 항목이다.
> Supabase 실프로젝트(`sgbhrahtewojmicwmxxu` · 서울)에서 **직접 돌려 확인했다.**

잡 1·2·3 은 5~10초 주기를 요구한다. 자료가 엇갈렸으므로 실측으로 판정했다.

| 확장 | 설치 버전 | 판정 |
|---|---|---|
| `pg_cron` | **1.6.4** | **초 단위 스케줄 지원** |
| `vector` | 0.8.2 (로컬 `pgvector:pg16` 은 0.8.6) | 정상 |

### 4.1 실측 결과

```
_probe_5s    '5 seconds'   → 22회 실행 · 평균 간격  5.01초 · 실패 0
_probe_10s   '10 seconds'  → 12회 실행 · 평균 간격 10.01초 · 실패 0
```

확인 쿼리:

```sql
SELECT name, default_version, installed_version
  FROM pg_available_extensions WHERE name IN ('pg_cron', 'vector');
```

### 4.2 ~~폴백안~~ — **폐기** ❌

**시세 폴링(우선순위 1 = 5초)을 pg_cron 으로 직접 돌릴 수 있다.**
따라서 "초 단위 미지원 시" 를 전제한 폴백안(on-demand 갱신 · piggyback 체결)은
**필요 없어졌고, 이 문서에서 삭제한다.**

> 폴백안의 아이디어 중 **`FOR UPDATE SKIP LOCKED` 로 동시 갱신을 한 요청만 잡는 것**은
> 폐기 대상이 아니다. 그건 초 단위 지원 여부와 무관하게 캐시 행 갱신에 쓰는 기법이라
> [E-04](../../erd/version2.0/E-04-market.md) 6장에 그대로 남아 있다.

**데이터 모델은 바뀌지 않는다** — 05 문서 2.1 이 예고한 대로다.

## 5. 관측성

v1.0 스케줄러는 실패 시 로그만 남겼다. 서버리스에서는 그 로그를 보기도 어렵다.

| 항목 | 처리 |
|---|---|
| 실행 이력 | `DataSyncLog(job_name, started_at, finished_at, status, rows_affected, error)` |
| 실패 알림 | Django Admin 대시보드에 **경고 배너**. 최근 실패 잡을 상단에 표시 |
| 연속 실패 | 3회 연속 실패 시 잡을 자동 비활성화하고 운영자에게 알림 (외부 API 장애 시 무한 재시도 방지) |
| pg_cron 자체 이력 | `cron.job_run_details` 테이블 조회 (Admin 에 읽기 전용 화면) |

## 6. 멱등성 원칙

**모든 잡은 두 번 돌아도 결과가 같아야 한다.**

| 잡 | 멱등 보장 |
|---|---|
| 정산 | `UNIQUE(participation, date)` + upsert |
| 마스터 동기화 | symbol 기준 upsert. **`TRUNCATE` 금지** |
| 코인 랭킹 | upsert. v1.0 의 `TRUNCATE` 후 재적재는 폐기 (동기화 중 빈 테이블이 보이는 창) |
| 주문 체결 | 주문 상태 전이로 보장. `FILLED` 는 다시 처리하지 않음 |
