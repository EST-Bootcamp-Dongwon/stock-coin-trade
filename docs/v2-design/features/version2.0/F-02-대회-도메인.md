> **문서 버전** v2.0 · **작성일** 2026-08-11 (KST) · **분류** 기능=신규 · 구현=신규작성
> **v1.0 대응** 1-13 투자랭킹(씨앗) · [인벤토리](../../v1.0-기능-인벤토리.md)

## 1. 개요

v2.0 의 중심 도메인이다. v1.0 에는 대회 개념이 전혀 없고, "전 회원 전기간 단일 랭킹"
API 하나(`/api/member/investor-rankings`)가 화면에 연결도 안 된 채 남아 있었다(결함 D-3).

대회는 다음을 정의한다.

- **누가** 참가하는가 (참가 신청·승인·정원)
- **언제까지** 하는가 (기간·거래 가능 시간)
- **얼마로** 시작하는가 (시작 자본)
- **무엇을** 살 수 있는가 (종목 유니버스·거래 불가 종목)
- **어떻게** 담아야 하는가 (편입 한도·섹터 한도·회전율)
- **누가 이겼는가** (수익률 + 관리 점수 상대평가)

이 중 규칙 판정은 [F-04 대회 규칙 엔진](F-04-대회-규칙엔진.md),
순위·정산은 [F-05 랭킹·정산·스냅샷](F-05-랭킹-정산-스냅샷.md)에서 다룬다.
이 문서는 **대회 자체의 생명주기**를 다룬다.

## 2. 대회 생명주기

```
DRAFT ──(운영자 공개)──▶ UPCOMING ──(시작일 도달)──▶ ONGOING
  준비중                    모집중                      진행중
                              │                           │
                              │                           │ (종료일 도달)
                              ▼                           ▼
                          CANCELLED                  SETTLING ──▶ CLOSED
                            취소                       정산중        종료
```

| 상태 | 의미 | 참가 신청 | 주문 | 랭킹 공개 |
|---|---|---|---|---|
| `DRAFT` | 운영자가 만드는 중. 참가자에게 안 보임 | ✕ | ✕ | ✕ |
| `UPCOMING` | 공개됨. 시작 전 | ✅ | ✕ | ✕ |
| `ONGOING` | 진행 중 | 설정에 따름 | ✅ (장 운영시간) | ✅ |
| `SETTLING` | 종료일 다음 영업일 06:00, 최종 정산 중 | ✕ | ✕ | 잠정치 |
| `CLOSED` | 정산 완료. 계좌 동결 | ✕ | ✕ | ✅ 확정 |
| `CANCELLED` | 운영자가 취소 | ✕ | ✕ | ✕ |

**상태 전이는 pg_cron 이 자동으로 한다.** 운영자가 매일 손으로 바꾸는 구조는
주말·공휴일에 깨진다. (→ [F-20 스케줄러](F-20-스케줄러.md))

> **Django 관점** — FastAPI 였다면 상태를 `str` 로 두고 서비스에서 검증했을 것이다.
> Django 는 `models.TextChoices` 를 쓴다. 클래스 하나로 **DB 값·화면 표시명·자동완성**이
> 한꺼번에 해결되고, Django Admin 이 이걸 읽어 드롭다운을 자동 생성한다.
>
> ```python
> class ContestStatus(models.TextChoices):
>     DRAFT     = "DRAFT",     "준비중"
>     UPCOMING  = "UPCOMING",  "모집중"
>     ONGOING   = "ONGOING",   "진행중"
>     SETTLING  = "SETTLING",  "정산중"
>     CLOSED    = "CLOSED",    "종료"
>     CANCELLED = "CANCELLED", "취소"
> ```

## 3. 대회 설정 항목

운영자가 대회를 만들 때 정하는 값들이다.
**하드코딩하지 않고 대회마다 다르게 줄 수 있어야 한다** — 1회 대회와 2회 대회의
규칙이 같으리라는 보장이 없기 때문이다.

### 3.1 기본 정보

| 항목 | 예시 | 비고 |
|---|---|---|
| 대회명 | "RFM 1회 대회" | |
| 설명 | 마크다운 | 규칙 안내문 |
| 자산군 (`asset_class`) | `STOCK` | **1차는 `STOCK` 만 허용.** 필드는 미리 만들어 둔다 |
| 시작일 / 종료일 | 2026-09-01 ~ 2026-09-30 | 날짜(KST). 실제 거래는 영업일·장중만 |
| 참가 신청 마감 | 2026-09-05 | 중도 참가 허용 여부를 이걸로 표현 |
| 정원 | 100명 (null = 무제한) | |
| 승인 방식 | 자동 / 운영자 승인 | 동아리 내부면 자동, 외부 공개면 승인 |
| 공개 범위 | 전체 공개 / 링크 공유 / 비공개 | |

### 3.2 자본·비용

| 항목 | 기본값 | 비고 |
|---|---|---|
| 시작 자본 | 100,000,000 (1억) | v1.0 `INITIAL_ASSET` 승계 |
| 매매 수수료 | **10bp (0.10%)** | 매수·매도 양방향. 대회 규칙값 |
| 매도세 | **20bp (0.20%)** | 매도 시에만. 대회 규칙값 |

> 연습 모드는 다른 요율(실제 국내 기준)을 쓴다. → [F-03](F-03-주문-체결엔진.md) 5장

### 3.3 규칙 (`rule_set` JSON)

규칙은 **JSON 한 칸에 담는다.** 규칙 항목이 늘어날 때마다 컬럼을 추가하고
마이그레이션을 돌리는 것보다, 스키마를 코드에서 검증하는 편이 낫다.

```jsonc
{
  "position_limit_pct": 15.0,              // 종목별 편입 한도 %
  "position_limit_exceptions": {           // 대형주 예외 한도
    "005930": 40.0,                        // 삼성전자
    "000660": 30.0                         // SK하이닉스
  },
  "sector_limit_multiplier": 2.0,          // 시장 섹터 비중의 N배까지
  "sector_limit_floor_pct": 10.0,          // 시장 비중 5% 이하 섹터는 이 값까지 허용
  "sector_limit_floor_threshold_pct": 5.0,
  "small_cap_threshold_krw": 1000000000000, // 시총 1조 미만 = 소형주
  "small_cap_total_limit_pct": 30.0,        // 소형주 합산 한도 %
  "min_market_cap_krw": 100000000000,       // 시총 1000억 미만 편입 불가
  "min_avg_turnover_krw": 3000000000,       // 5일 평균 거래대금 30억 이하 매수 불가
  "new_listing_block_days": 6,              // 신규·재상장 후 6영업일간 거래 불가
  "block_supervised": true,                 // 관리·투자주의/경고/위험 종목 차단
  "weekly_turnover_min_pct": 5.0,           // 주간 회전율 최저
  "weekly_turnover_violation_limit": 3,     // 위반 허용 횟수
  "score_weight_return": 0.7,               // 수익 점수 가중
  "score_weight_management": 0.3            // 관리 점수 가중
}
```

**기본 `rule_set` 은 코드에 상수로 두고, 대회 생성 시 복사해 넣는다.**
이렇게 하면 기본값을 바꿔도 진행 중인 대회의 규칙이 흔들리지 않는다.

### 3.4 규칙 스냅샷 원칙 ★

> **대회 시작 시점에 규칙과 종목 정보를 얼어붙게 한다.**

타임폴리오 규칙에 명시된 원칙이다 — *"개별 종목의 GICS 는 대회시작일 직전 영업일 기준으로
적용합니다(대회 기간 중 변동은 없음)."*

우리도 같은 원칙을 따른다. 대회가 `UPCOMING` → `ONGOING` 으로 넘어가는 순간
다음을 **복사해 고정**한다.

| 고정 대상 | 왜 |
|---|---|
| 종목별 업종분류 (KRX 업종) | 기간 중 업종이 바뀌면 섹터 한도 판정이 흔들린다 |
| 시장 섹터 비중 | 섹터 한도의 기준값. 매일 바뀌면 어제 합법이던 포트가 오늘 위반이 된다 |
| 대형주 예외 한도 | 대회 중 예외 종목을 추가하면 불공정하다 |

이 스냅샷은 `ContestUniverse` 로 저장한다(→ 5장).
반면 **시총·거래대금·관리종목 지정은 매일 갱신**한다. 이건 "지금 살 수 있는가"의
판정이라 최신값이 맞다.

## 4. 참가

### 4.1 참가 흐름

```
[참가자]                          [시스템]
대회 목록에서 선택
  │
  ├─ 참가 신청 ─────────────▶ 자격 검증
  │                            · 대회 상태가 UPCOMING/ONGOING 인가
  │                            · 신청 마감일이 지나지 않았는가
  │                            · 정원이 남았는가
  │                            · 이미 참가하지 않았는가
  │                                    │
  │                            승인 방식에 따라
  │                            ├ 자동 → APPROVED
  │                            └ 수동 → PENDING (운영자 승인 대기)
  │                                    │
  │◀──────────────────────────  APPROVED 시 Account 생성
                                 · mode=CONTEST, contest=이 대회
                                 · cash = 대회 시작 자본
                                 · 별칭(nickname) 입력받아 저장
```

### 4.2 별칭(nickname)

랭킹 화면에 실명을 노출하지 않는다. 타임폴리오와 동일하게 **대회별 별칭**을 쓴다.

- 대회마다 다른 별칭 사용 가능 (`Participation.nickname`)
- 대회 내 유일해야 함 (`UNIQUE(contest, nickname)`)
- 미입력 시 `"참가자{번호}"` 자동 부여
- 운영자는 Django Admin 에서 실명↔별칭 대응을 볼 수 있다

### 4.3 참가 상태

| 상태 | 의미 |
|---|---|
| `PENDING` | 승인 대기 |
| `APPROVED` | 참가 확정. 계좌 생성됨 |
| `REJECTED` | 운영자 거절 |
| `DISQUALIFIED` | 실격 (회전율 4회 위반 · 부정행위) — **계좌는 남고 랭킹에서만 제외** |
| `WITHDRAWN` | 본인 포기 |

> **실격 처리 원칙** — 계좌·주문 이력을 지우지 않는다. 지우면 회고가 불가능하고,
> 실격 판정이 잘못됐을 때 되돌릴 수 없다. `is_ranked = False` 로만 만든다.

## 5. 필요 데이터 모델 (ERD 세션 입력)

> 상세 스키마는 다음 세션(`erd/version2.0`)에서 확정한다. 여기서는 **기능이 요구하는 것**만 적는다.

| 모델 | 핵심 필드 | 비고 |
|---|---|---|
| `Contest` | name, description, asset_class, status, start_date, end_date, entry_deadline, capacity, approval_mode, visibility, initial_capital, fee_bp, tax_bp, rule_set(JSON) | 대회 본체 |
| `Participation` | contest, member, nickname, status, is_ranked, joined_at, disqualified_reason | 회원 × 대회 |
| `Account` | member, contest(nullable), mode, cash, is_frozen, created_at | **모드별 계좌.** 대회 계좌는 contest 가 있고, 연습 계좌는 null |
| `ContestUniverse` | contest, symbol, sector_code, sector_name, is_tradable, frozen_at | 대회 시작 시 고정된 종목·업종 스냅샷 |
| `ContestSectorWeight` | contest, sector_code, market_weight_pct | 시장 섹터 비중 (시작 시 고정) |

### 5.1 `Account` 가 왜 필요한가 — v1.0 과의 대비

| | v1.0 | v2.0 |
|---|---|---|
| 현금 위치 | `member.asset` 단일 칸 | `Account.cash` (회원당 여러 개) |
| 포지션 소유자 | `member_id` | `account_id` |
| 대회 지원 | 불가 | 대회별 계좌 분리 |
| 계좌 초기화 | 코인만 안 지워짐 (결함 D-5) | 해당 계좌만 통째로 초기화 |

**모든 포지션·주문 테이블의 FK 가 `member` → `account` 로 바뀐다.**
이게 v2.0 데이터 모델에서 가장 큰 변화다.

## 7. v1.0 대비 차별점 (문제 정의)

벤치마크(`contest.timefolio.net`)에서 발견한 결함 3가지가 v2.0 의 차별점이다.

| 벤치마크 결함 | v2.0 대응 |
|---|---|
| ① **실시간 시세·검색이 없다** — "당사는 데이터 서비스를 하는 회사가 아니고 시세를 재배포하지 않음. 호가창·시세·차트는 증권사 HTS 등을 참고" 라는 의도적 정책 | v1.0 이 이미 시세 파이프라인(yfinance·네이버·업비트)을 갖고 있다. **KIS 실호가를 더해 화면 안에서 시세·호가·차트를 다 본다** |
| ② **신규주문 창에 현재가·내 평단이 없다** | 주문 모달에 현재가·등락률·내 평단·손익분기가·잔여 현금·한도 여유를 전부 표시 |
| ③ **50등 이후 참가자는 포트폴리오 조회 불가** | 동아리 대회이므로 **전 참가자 포트폴리오를 공개**한다. 서로 배우는 게 목적 |
