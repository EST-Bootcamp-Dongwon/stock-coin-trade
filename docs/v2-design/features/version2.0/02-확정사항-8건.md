## 8번 상세 — 시세 캐시 저장소를 Postgres 로 정한 이유

사용자 지시로 리서치 후 결정했다. 조건은 **"비용 부담이 없을 것"**이었다.

### 후보 비교

| 후보 | 판정 | 이유 |
|---|---|---|
| **Supabase Postgres 테이블** | **채택** | 아래 4가지 근거 |
| Postgres + Django 로컬 메모리 2단 | 기각 | 배포가 **Vercel 서버리스**라 프로세스 메모리는 콜드스타트마다 소멸하고 인스턴스 간 공유도 안 된다. 히트율이 사실상 0이라 복잡도만 늘고 이득이 없다 |
| Upstash Redis | 기각 | 기능적으로는 가장 자연스럽지만 계정·키·티어 관리가 새로 늘어난다. 무료 티어 요청수 상한도 있어 "비용 부담 없을 것" 조건에서 관리 부담이 크다 |

### 채택 근거 4가지

1. **서버리스에서 프로세스 메모리는 무의미하다.**
   v1.0 결함 D-9(모든 캐시·rate limit 이 전역 `dict`)의 원인이 바로 이것이다.
   같은 실수를 반복하지 않으려면 캐시는 처음부터 공유 저장소여야 한다.

2. **KIS 유량 제한 때문에 전역 호출 예산이 필요하다.**
   KIS 모의투자 API 는 **초당 5건** 제한이다(실전 20건).
   "지금 이 종목을 마지막으로 언제 조회했는가"를 **모든 인스턴스가 함께** 알아야
   중복 호출을 막을 수 있다. 메모리 2단이면 각 인스턴스가 독립적으로 "나는 안 불렀다"고
   판단해 동시에 호출하고 `EGW00201`(유량 초과)을 맞는다.

3. **추가 비용·계정이 0이다.** 이미 쓰는 Supabase 안에 테이블을 만들 뿐이다.

4. **pg_cron 과 같은 트랜잭션에 있다.**
   시세 갱신 잡과 미체결 주문 추종을 하나의 SQL 트랜잭션에서 처리할 수 있어
   "시세는 갱신됐는데 주문은 옛 가격으로 체결"되는 창이 생기지 않는다.

### 지연(latency) 보완책

Postgres 왕복은 메모리보다 느리다. 다음 두 가지로 보완한다.

- **요청 단위 캐시만 허용.** 하나의 HTTP 요청 안에서 같은 종목을 여러 번 조회하면
  두 번째부터는 파이썬 딕셔너리에서 꺼낸다. 요청이 끝나면 버린다.
  → **요청을 넘어서 사는 메모리 캐시는 금지**한다. 이게 D-9 의 재발 방지선이다.
- **화면 단위 배치 조회.** 종목 20개를 그리는 화면은 20번 조회하지 않고
  `WHERE symbol IN (...)` 한 번으로 가져온다.

### 검증이 필요한 전제 ⚠️

**pg_cron 의 초 단위 스케줄 지원 여부**는 자료마다 엇갈린다.
Supabase 공식 문서는 "1~59초 지원"이라 하고, 커뮤니티 논의에는
"Supabase 의 pg_cron 은 1.4-1 이고 초 단위는 1.5+ 부터"라는 (더 오래된) 언급이 있다.

- **구현 착수 시 실제 프로젝트에서 `SELECT extension_version FROM pg_available_extensions WHERE name='pg_cron'` 로 확인한다.**
- **폴백안**: 초 단위가 안 되면 `pg_cron` 은 1분 주기로 두고,
  그보다 잦은 갱신이 필요한 종목은 **요청 시점 on-demand 갱신**(TTL 만료 시 그 요청이 직접 KIS 호출)으로
  처리한다. 이 경우 동시 호출 방지를 위해 `SELECT ... FOR UPDATE SKIP LOCKED` 로 갱신 권한을 한 요청만 잡는다.
