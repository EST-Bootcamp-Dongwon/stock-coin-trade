# F-03. 주문·체결 엔진

> **문서 버전** v2.0 · **작성일** 2026-08-11 (KST) · **분류** 기능=개선 · 구현=수정포팅
> **v1.0 대응** 1-3 주식거래(`stock_trading.execute_order`) · 1-2 코인거래
> **핵심 확정** KIS 실호가 도입 + 전체 재현 · 즉시 체결 + 예약주문 (비동기 워커 없음)

---

## 1. 개요와 절충안

사용자 확정은 두 가지였고, 그대로 두면 서로 부딪힌다.

- **"KIS 실호가 도입 + 전체 재현"** — 타임폴리오 체결은 *상대 n호가 잔량 소진 →
  남은 잔량은 시장 체결 추종* 이라 **비동기 처리**가 전제다.
- **"즉시 체결 + 예약주문만"** — 비동기 워커 아키텍처는 만들지 않는다.

### 절충 설계 ★

> **주문은 즉시 접수·즉시 체결을 시도한다. 상대호가 잔량으로 채울 수 있는 만큼은
> 그 자리에서 체결하고, 남은 잔량은 `PARTIAL`(부분체결) 상태로 남는다.
> 남은 잔량은 별도 워커가 아니라 시세 폴링 잡(pg_cron)이 돌 때마다 시장 체결을 추종한다.**

이러면 얻는 것:

- 참가자는 주문 버튼을 누르는 즉시 결과를 본다 (v1.0 의 즉시 체결 UX 유지)
- 호가 잔량보다 큰 주문은 한 번에 다 체결되지 않는다 (타임폴리오의 시장 충격 개념 반영)
- 비동기 워커·큐·멱등키·재시도 설계가 필요 없다. 미체결 추종은 **이미 도는 시세 잡에 얹는다**

포기하는 것: 시간분할 주문, 과주문 후 대기(n분 정지) → **v2.1**.

## 2. 주문 상태 머신

```
                   유효성 검증 실패
        ┌──────────────────────────▶ REJECTED (거부)
        │
[주문 입력] ──▶ ACCEPTED (접수) ──▶ 즉시 체결 시도
                    │                    │
                    │                    ├─ 전량 체결 ──▶ FILLED (체결완료)
        장 시작 전  │                    ├─ 일부 체결 ──▶ PARTIAL (부분체결)
        예약 대기   │                    └─ 미체결   ──▶ ACCEPTED 유지
                    │                              │
                    ▼                              │ (시세 폴링마다 추종)
               PENDING_OPEN                        │
              (장 시작 대기)                        ▼
                    │                        FILLED / PARTIAL
                    └──▶ 장 시작 시 체결 시도
                                                   │
                    사용자 취소 / 장 마감 ──────────▶ CANCELLED (취소)
```

| 상태 | 의미 | 잔량 |
|---|---|---|
| `PENDING_OPEN` | 장외 접수. 다음 장 시작 시 처리 | 전량 |
| `ACCEPTED` | 접수됨. 체결 대기 | 전량 |
| `PARTIAL` | 일부 체결. 나머지 대기 | 일부 |
| `FILLED` | 전량 체결 | 0 |
| `CANCELLED` | 취소 (사용자 / 장마감 미체결 자동취소) | 잔량 소멸 |
| `REJECTED` | 접수 거부 (규칙 위반 · 잔고 부족) | — |

> **장 마감 시 미체결 주문은 자동 취소한다.** 다음 날로 넘기지 않는다.
> 넘기면 밤새 뉴스로 상황이 바뀐 뒤 옛 지정가가 체결되는 문제가 생긴다.

## 3. 주문 입력 항목

### 3.1 대회 모드 (타임폴리오 방식)

| 항목 | 값 | 비고 |
|---|---|---|
| 종목 | 검색 선택 | 거래 불가 종목은 검색 결과에 **노란색 경고**, 선택 시 에러 |
| 매수/매도 | `BUY` / `SELL` | |
| **주문 비중(%)** | 순자산 대비 % | **수량이 아니다.** 접수 시점에 수량으로 환산 |
| 가격 유형 | `상대호가` / `자기호가` / `지정가` / `STOP` | 4종 |
| 호가 단계 | 1~10 | 상대호가·자기호가일 때만 |
| 지정가 | 숫자 | 지정가일 때만 |
| STOP 가격 | 숫자 | STOP 일 때만 |
| 실행 방식 | `즉시 실행` | 시간분할은 v2.1 (화면에 비활성 + "v2.1 예정" 표시) |

**주문 비중(%) 환산식**

```
주문 수량 = floor( 순자산 × 비중% / 100 / 기준가 )
```

- 순자산 = 현금 + 보유 종목 평가액 합
- 기준가 = 가격 유형에 따라 결정된 지정가 (아래 4장)
- 매도는 **보유 수량 대비 %가 아니라 순자산 대비 %**다. 타임폴리오와 동일.
  보유분보다 많으면 보유 전량으로 잘라낸다.

### 3.2 연습 모드 (v1.0 방식 유지)

| 항목 | 비고 |
|---|---|
| 수량 직접 입력 / 금액 입력 / %비율 버튼 | v1.0 UX 그대로 |
| 가격 유형 | `시장가` / `지정가` |
| 코인은 원화 금액(`buyKrw`) 입력 → 수량 자동 산출 | v1.0 `crypto.py` 로직 승계 |

## 4. 가격 유형 4종의 의미

타임폴리오 규칙 전문 기준. **매수 주문에서 자기호가 = 매수호가, 상대호가 = 매도호가.**
매도는 반대다.

| 유형 | 지정가가 되는 값 | 성격 |
|---|---|---|
| **상대호가 n** | 매수면 매도n호가 / 매도면 매수n호가 | **공격적.** 거래소 "최유리지정가"와 비슷하되 n번째를 고를 수 있다 |
| **자기호가 n** | 매수면 매수n호가 / 매도면 매도n호가 | **소극적.** 거래소 "최우선지정가"와 비슷. 기존 잔량이 먼저 체결된 뒤 내 차례 |
| **지정가** | 입력값 | 그대로 |
| **STOP** | — | 시장가가 STOP 가격에 닿으면 그 시점에 **시장가 주문**이 나간다 |

### 4.1 상한가·하한가 특례

> 상(하)한가에 들어간 종목의 자기호가 매도(수) 주문은 상(하)한가에 체결된다.

### 4.2 STOP 주문 처리

STOP 은 즉시 체결하지 않는다. `ACCEPTED` 로 남아 있다가 **시세 폴링 잡**이
조건 도달을 감지하면 그 시점에 시장가로 전환해 체결한다.

- 매도 STOP: 현재가 ≤ STOP 가격 → 발동 (손절)
- 매수 STOP: 현재가 ≥ STOP 가격 → 발동 (추격 매수)

## 5. 체결 알고리즘

### 5.1 즉시 체결 (주문 접수 시점)

```
1. 호가 조회
   · KIS 실호가 10단계를 orderbook_cache 에서 읽는다 (→ F-16)
   · 캐시가 오래됐으면(TTL 초과) 이 요청이 직접 KIS 를 호출해 갱신
2. 지정가 결정 (4장의 유형별 규칙)
3. 상대호가 잔량 소진 체결
   · 상대 최우선호가부터 순서대로, 내 지정가 조건을 만족하는 호가의 잔량만큼 체결
   · 각 호가 단계마다 체결가가 다르므로 가중평균 체결가를 만든다
4. 지정가가 상대 10호가를 넘는 경우
   · 1~10호가의 "평균 잔량"이 1틱 간격으로 11호가부터 형성되어 있다고 가정하고 계속 체결
   · (타임폴리오 규칙: 실제 시장 상황보다 유리한 가정임을 화면에 명시)
5. 남은 잔량 → PARTIAL 로 저장. 시장 체결 추종 대상이 된다
```

### 5.2 시장 체결 추종 (시세 폴링 시점)

```
pg_cron 시세 갱신 잡이 돌 때마다:
  · PARTIAL / ACCEPTED 상태의 대회 주문을 모두 스캔
  · 직전 폴링 이후의 체결가(현재가 변화)를 확인
  · 매수 주문: 시장 체결가 ≤ 내 지정가 → 그 가격으로 체결
  · 매도 주문: 시장 체결가 ≥ 내 지정가 → 그 가격으로 체결
  · STOP 주문: 발동 조건 확인 → 시장가 전환
```

> **v1.0 대비 정직성** — v1.0 은 호가창을 현재가에서 파생 생성했고
> (`stock.js` 의 5단계 호가), 체결은 항상 현재가 전량 즉시였다.
> v2.0 대회 모드는 실호가를 쓰므로 "큰 주문은 불리한 가격에 체결된다"는
> 실제 감각이 생긴다. **연습 모드는 v1.0 방식(현재가 전량 즉시)을 유지**한다.

## 6. 거래 비용

| 모드 | 매매 수수료 | 매도세 | 근거 |
|---|---|---|---|
| **대회** | **10bp (0.10%)** 매수·매도 양방향 | **20bp (0.20%)** 매도 시 | 타임폴리오 대회 규칙값 |
| **연습(주식)** | 0.015% 양방향 | 0.18% 매도 시 | 실제 국내 기준(위탁수수료 + 증권거래세·농특세) |
| **연습(코인)** | 0.05% 양방향 | 없음 | 업비트 기준 |
| **연습(대체자산)** | 없음 | 없음 | v1.0 유지. 증거금 개념만 |

### 계산 규칙

```
매수:  차감 현금 = 체결금액 + 수수료
매도:  가산 현금 = 체결금액 - 수수료 - 매도세

수수료 = floor(체결금액 × 수수료율)
매도세 = floor(체결금액 × 매도세율)
```

- **원 단위 절사**(`floor`)한다. 소수점 현금이 생기면 표시가 지저분해진다.
- 대회 요율은 `Contest.fee_bp` / `Contest.tax_bp` 에서 읽는다. 하드코딩 금지.
- 수수료·세금은 `Order` 행에 **별도 컬럼으로 저장**한다. 사후에 재계산하지 않는다.

## 7. 잔고·포지션 갱신

v1.0 의 검증된 로직을 승계한다. 주체만 `member` → `account` 로 바뀐다.

### 7.1 동시성 제어

```python
# v1.0 (SQLAlchemy)
db.refresh(member, with_for_update=True)

# v2.0 (Django ORM) — 같은 의도
account = Account.objects.select_for_update().get(pk=account_id)
```

> **Django 관점** — FastAPI + SQLAlchemy 의 `with_for_update=True` 는
> Django 에서 `select_for_update()` 다. 다만 Django 는 **`transaction.atomic()`
> 블록 안에서만** 이 호출이 유효하다. 밖에서 부르면 `TransactionManagementError` 가 난다.
>
> ```python
> from django.db import transaction
>
> with transaction.atomic():
>     account = Account.objects.select_for_update().get(pk=account_id)
>     # ... 검증 → 차감 → 포지션 갱신 → 주문 기록
> ```

### 7.2 평단 재계산

v1.0 공식 그대로.

```
매수: 새 평단 = (기존 수량 × 기존 평단 + 체결 수량 × 체결가) / (기존 수량 + 체결 수량)
      주식은 int 절사, 코인은 소수점 8자리 유지
매도: 평단 불변. 매수원금을 매도 비율만큼 차감
      수량이 0 이 되면 포지션 행 삭제
```

### 7.3 잔고 부족 검증

- **수수료·세금을 포함한 금액**으로 검증한다. v1.0 은 수수료가 없어 체결금액만 봤다.
- 매수: `account.cash >= 체결금액 + 수수료` 여야 한다.
- 부족하면 `REJECTED` + 필드 단위 에러 메시지(v1.0 의 `{"field":..., "error":...}` 패턴 승계).

### 9.1 v1.0 대비 통합

v1.0 은 `stock_order` · `alternative_order` 가 따로 있고 **코인 주문 이력은 아예 없었다**(결함 D-4).
v2.0 은 `Order` **하나로 통합**하고 `asset_class` 로 구분한다.

| v1.0 | v2.0 |
|---|---|
| `stock_order` | `Order(asset_class="STOCK")` |
| `alternative_order` | `Order(asset_class="ALT")` |
| (없음) | `Order(asset_class="CRYPTO")` ← **신설** |
| `stock_position` / `alternative_position` / `hold_crypto` | `Position(asset_class=...)` |

이렇게 하면 [F-10 거래이력](F-10-거래이력.md)이 자산군 통합 조회가 된다.
