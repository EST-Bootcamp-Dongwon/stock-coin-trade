## 1. 설계의 출발점

### 1.1 v1.0 의 근본 문제

v1.0 은 회원 한 명이 **현금 1억(`member.asset`) 한 칸**을 갖고 주식·코인·대체자산을
전부 그 한 칸으로 거래했다. 그 결과:

- "누가 잘했는가"를 물으면 답이 하나뿐이고 **규칙을 걸 자리가 없다**
- 주식 계좌를 초기화해도 코인이 남아 **총자산이 1억을 넘는다** (결함 D-5)
- 자산군이 섞여 **자산군별 실력을 측정할 수 없다**

### 1.2 v2.0 의 답 — 계좌 분리

```
Member
 ├── Account(PRACTICE_STOCK)   현금 1억 · 주식
 ├── Account(PRACTICE_CRYPTO)  현금 1억 · 코인
 ├── Account(PRACTICE_ALT)     현금 1억 · 대체자산
 └── Account(CONTEST, 대회별)   시작자본 = 대회 설정값
```

**모든 포지션·주문의 FK 가 `member` → `account` 로 바뀐다.**
이것이 v2.0 데이터 모델의 가장 큰 변화다.

→ 상세 [F-00 모드 체계와 범위 경계](F-00-모드체계와-범위경계.md)

## 6. v2.0 1차 릴리스 범위 경계

### 6.1 들어가는 것

```
[기반]   계정·계좌 4종 · Django Admin · pg_cron 14잡
[대회]   대회 CRUD·참가·규칙엔진·체결엔진·랭킹·일별스냅샷·Top Pick·정산
[연습]   주식·코인·대체자산 + 물타기 + Pine(수동)
[데이터] KIS 실호가 · pykrx 일배치 · 업비트 · 네이버/yfinance 폴백 · KRX 뉴스
[부가]   AI 분석 · 지식검색(pgvector) · 학습 콘텐츠 · Open API · 웹 데이터 수집기
```

### 6.2 v2.1 로 미루는 것 (명시적 유예)

| 항목 | 이유 |
|---|---|
| 시간분할 주문 · 과주문 후 대기 | 비동기 워커 아키텍처 선행 필요 |
| 주문 정정 | 미체결 잔량 관리가 얽힘. 1차는 취소 후 재주문 |
| 기업 이벤트 (증자·배당·액면변경·분할합병) | 데이터 소스가 따로 필요. **1차는 운영자 수동 조정** |
| 동시호가(단일가) 세션 | 1차는 09:00~15:30 연속 세션으로 단순화 |
| Pine 백테스트 | 과거 봉 저장이 선행되어야 함 |
| Pine 자동 실행 · 공매도 | 확정 사항 6·7번 |
| 코인·대체자산 **대회** | v2.2. `asset_class` 필드만 1차에 마련 |
| 소셜 로그인 · 이메일 인증 | 1차는 아이디/비밀번호 |
| 다크 모드 | 색상 토큰만 잡아둠 |

### 6.3 유예 원칙 ★

> **미루는 기능은 화면에 "v2.1 예정"으로 표시하거나 아예 노출하지 않는다.**
> 버튼만 있고 동작하지 않는 상태(v1.0 결함 D-1·D-3 패턴)를 반복하지 않는다.

## 7. 관통하는 설계 원칙 3가지

[03-결함 처리방침](03-v1.0결함-11건-처리방침.md)에서 세운 원칙이다.
모든 명세 문서가 이 셋을 따른다.

### ① 죽은 코드를 남기지 않는다

v1.0 의 결함 D-1·D-2·D-3 은 전부 **"만들었는데 화면에 안 붙은 것"**이었다.
**기능을 만들면 반드시 진입점을 만든다. 못 만들면 1차 범위에서 뺀다.**

### ② 화면에 보이지 않는 사실은 없는 것과 같다

파생 호가, 시뮬레이션 가격, "AI Sheet에 AI 없음", GICS 대신 KRX 업종 —
전부 **코드에만 있고 사용자에게는 안 보이던 사실**이다.
**배지·주석으로 화면에 드러낸다.**

### ③ 서버리스 전제를 처음부터 지킨다

결함 D-8·D-9 는 **"프로세스가 계속 살아 있다"는 전제**에서 나왔다.
**요청을 넘어서 사는 상태는 전부 DB 에 둔다.**
